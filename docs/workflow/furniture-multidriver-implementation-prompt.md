# 가구용 멀티 드라이버 구현 모델용 프롬프트

GhostHunter 저장소에서 가구 분해·조립 아이템(가구용 멀티 드라이버)을 구현하라. 아래를 작업 지시로
쓰되, 게임 규칙의 최신 권위는 `docs/project/furniture-multidriver-system.md`다.
**기획서만 다시 쓰고 끝내지 말고, 확정된 범위의 코드·배선·검증·문서 갱신까지 수행하라.**

> 이 기능은 **오브젝트를 치환**한다(큰 가구 1개 ↔ 작은 가구 N개). 지금까지의 어떤 작업보다
> 기존 가구·맵·던지기 시스템을 깊게 건드린다. **§1.3의 블로커를 먼저 해소하지 않으면 착수하지 마라.**

## 1. 컨텍스트 로드와 범위 확인

### 1.2 브랜치 확인

이 저장소는 최근 한 작업 트리에서 여러 기능을 동시에 진행해 커밋이 엉킨 적이 있다. 착수 전
`git status`와 현재 브랜치를 확인하고, **커밋되지 않은 남의 작업이 있으면 그것을 먼저 커밋할지
사용자에게 물어라.** 네 작업은 별도 브랜치(`feature/furniture-multidriver` 등)에 담되, 의존하는
선행 작업이 커밋되지 않았다면 그 순서를 사용자와 합의하고 진행하라.

### 1.3 착수 전 반드시 물을 것 (블로커)

기획서 §8의 미결정 13건 중 **아래는 없으면 구현이 불가능하다. 한 번에 묶어 사용자에게 물어라.**
**제안값을 확정값처럼 코드·테스트·문서에 고정하지 마라.**

| # | 물을 것 | 없으면 막히는 것 |
| --- | --- | --- |
| MD-1 | **분해 가능한 큰 가구 목록과 각 가구의 부품 구성.** 33종 중 무엇이 분해되고, 각각 어떤 부품 몇 개로 나뉘는가 | 분해·조립 전체. 데이터가 없으면 아무것도 만들 수 없다 |
| MD-2 | **조립 영역의 위치·크기·개수.** 드릴 카 본체가 아직 없다(세이프 존만 임시 구현) | 조립 기능 전체 |
| MD-5 | **아이템 획득·장착 경로.** 퀵슬롯 슬롯을 하나 쓰는가, 스테이지 시작 시 전원 지급인가 | "손에 장착" 전제(§3.1) |
| MD-10 | **분해된 작은 가구를 잡거나 던질 수 있는가.** 무게·아웃라인·탐지 마커 대상인가 | 부품의 물리·상호작용 설계 |
| MD-11 | **"이동"의 정의.** 이동 입력인가 실제 변위인가, 시점 회전·웅크리기·점프는 포함인가 | 행동 중단 판정(§3.2) |
| MD-12 | **"귀신에게 공격당함"의 시점.** 포착인가 어택 성립인가 | 행동 중단 판정(§3.2) |

**이번 범위 밖으로 미뤄라** — MD-3(짐칸·반출, MG-22 대기), MD-4(상점·수리 가격),
MD-6(가구 내구도 증감 원인), MD-13(스테이지 종료 시 잔여 부품). 새로 정하지 마라.

**구현 중 확인** — MD-7(내구도 0 취급), MD-8(분해·조립 가능 여부 사전 표시), MD-9(동시 시도·권위).

답변을 기다리는 동안 §3의 기존 코드 조사, 순수 판정 로직 설계, 테스트 골격 같은 독립 작업은 계속하라.

## 2. 구현 목표 (기획서 확정 범위)

- **장착** — 드라이버를 손에 든 상태에서만 동작한다. 사망 중에는 쓸 수 없다.
- **분해** — 분해 가능한 큰 가구에 우클릭 → 행동 시간 → 큰 가구가 사라지고 부품 N개가 그 자리에
  공중 1m에서 생성되어 떨어진다.
- **조립** — 조립 영역에 올바른 부품이 전부, 바닥에 놓인 상태로 있을 때 실루엣이 초록이 되고,
  실루엣에 우클릭 → 행동 시간 → 부품이 사라지고 큰 가구가 영역 중앙에 생성된다.
- **조립 성립 판정** — 다른 가구의 부품이 섞이거나 개수가 초과되면 불가(붉은 실루엣). 같은 종류의
  큰 가구에서 나온 부품은 출처를 구분하지 않는다. **이 두 규칙이 이 기능의 핵심이다.**
- **행동 시간** — 내구도 > 15면 3초, ≤ 15면 9초. 시작 시점 내구도로 판정한다. 이동·스킬 사용·
  귀신 공격 시 즉시 중단되고 **처음부터** 다시 해야 한다. 중단되면 내구도는 닳지 않는다.
- **내구도** — 성공 완료 시에만 5 감소, 완료 이후에 적용. 0 미만으로 내려가지 않는다.
- **가구 내구도 전파** — 분해 시 전 부품이 같은 값을 상속, 조립 시 평균(소수점 버림).
- **연출** — 중앙 하단 로딩바, 실패 시 좌우 2회 흔들림 + "분해 실패"/"조립 실패", 손목 돌리기
  애니메이션 반복, 실루엣 3색(`#FFFFFF` 투명도 50 / `#78C664` / `#D66565`).

경로는 `Assets/Scripts/` 기준이다. **아래는 문서 작성 시점의 정적 확인이므로 구현 전에 현재 코드를
다시 대조하라.**

| 경로 | 확인할 내용 |

특히 아래를 빠뜨리지 마라.

1. **ADR-0009와 정면으로 부딪힌다.** 하드 룰은 "던질 수 있는 가구는 씬에 배치된 실제 가구이며
   런타임 스폰하지 않는다"인데, 분해는 본질적으로 새 오브젝트를 만든다. **임의로 `NetworkObject.Spawn`을
   쓰지 마라.** 먼저 청소 얼룩·랜덤 가구가 쓰는 **씬 풀 + 서버 재배치** 방식으로 풀 수 있는지 검토하고,
   그래도 런타임 스폰이 필요하다면 **ADR을 새로 쓰고 사용자 승인을 받아라.**
2. **런타임 생성 `NetworkObject`는 `GlobalObjectIdHash`가 0이라 NGO가 구분하지 못한다**
   (`CLAUDE.md` §5, `conventions/unity-assets.md` §5.2). 프리팹 스폰이면 `DefaultNetworkPrefabs`
   등록이 필요하고, 씬 배치면 씬 저장·Build Settings 포함 여부가 해시에 영향을 준다.
3. **`.inputactions`는 `AssetDatabase.SaveAssets()`로 저장되지 않는다.** 이 에셋은 JSON 원본이
   진실이고, 인메모리 `InputActionAsset`을 고쳐도 디스크에 반영되지 않는다. **반드시
   `asset.ToJson()`을 `File.WriteAllText`로 원본 경로에 쓰고 `AssetDatabase.ImportAsset`으로
   재임포트하라.** 저장된 줄 알고 넘어가면 나중에 액션이 통째로 사라진 채 커밋된다(실제 발생).
   저장 후 파일에서 액션 이름을 직접 grep 해 확인하라.
4. **행동 시간 중단은 "입력 잠금"이 아니라 "취소 판정"이다.** 굴착처럼
   `SetSkillInputLocked`로 막아 버리면 기획(이동하면 취소)이 성립하지 않는다. 반대로 아무 잠금도
   없으면 행동 중 던지기·스킬이 나간다. **무엇을 막고 무엇을 취소 트리거로 볼지 MD-11 답변에
   맞춰 설계하고, 잠금을 걸었다면 정상 완료·취소·디스폰 **세 경로 모두**에서 반드시 풀어라.**
5. **로컬 차단만으로 끝내지 마라.** 분해·조립 요청은 서버가 발신자·장착 여부·생존·거리·대상 유효성·
   조립 영역 점유 상태를 **다시** 검증해야 한다. 행동 시작 직전에 보내고 늦게 도착한 요청,
   행동 중 대상이 사라진 경우, 두 플레이어가 같은 대상에 동시에 시도하는 경우(MD-9)를 처리하라.
6. **분해되는 가구가 누군가에게 잡혀 있을 수 있다.** 삭제 전에 홀더를 정리하지 않으면 홀더가 영구
   잔류한다. `FurnitureGrabTarget.ServerForceRelease(forced: true)`(발사 없는 해제) 경로가 이미 있다.
7. **사망 처리와 충돌하지 않게 하라.** 사망 시 생존 조작은 이미 전부 잠기고 가구 홀드는 자동
   해제된다(`spectator-system.md`). 행동 중 사망하면 행동도 취소돼야 하며, 사망자의 요청은 서버가
   거절해야 한다. 이미 있는 게이팅을 중복 구현하지 마라.
8. **조립 영역 점유 판정은 매 프레임 전역 검색으로 만들지 마라.** 트리거 진입/이탈 기반으로
   관리하고, "바닥에 놓인 상태" 판정 기준(속도·접지·홀더 없음)을 명시적으로 정의하라.

## 4. 구현과 정리 절차

**단계를 나눠 진행하고, 각 단계가 컴파일·테스트를 통과한 뒤 다음으로 가라.**

1. **FM-IMPL-1 데이터·장착** — 분해 가능 가구와 부품 구성을 `ScriptableObject`로 정의(MD-1 답변 반영),
   드라이버 장착 경로 연결(MD-5 답변 반영), 우클릭 액션 신설. 수치(3초·9초·5감소·15임계)는 전부 SO로.
2. **FM-IMPL-2 분해** — 대상 판정 → 서버 요청 → 행동 시간·중단 → 서버에서 큰 가구 제거·부품 배치·
   가구 내구도 상속 → 아이템 내구도 감소. 홀더·물리 정리 포함.
3. **FM-IMPL-3 조립** — 조립 영역 점유 관리, **조립 성립 판정을 순수 로직으로 분리**(부품 집합 →
   조립 가능 여부·대상 가구), 실루엣 3색 표시, 서버 조립 실행·내구도 평균.
4. **FM-IMPL-4 연출·정리** — 로딩바 UI, 실패 흔들림·문구, 손목 애니메이션, 공중 1m 낙하.
   디스폰·씬 종료·사망·부활에서 행동 상태·잠금·구독·실루엣이 남지 않게 정리하라.

전 단계 공통 제약:

- 새 패키지·Unity/URP 버전·프로젝트 설정·Steam 설정·맵 규모를 바꾸지 마라.
- 가구 물리는 **서버 권위**(ADR-0010)를 유지하고, 클라이언트는 입력·의도만 보낸다.
- 입력은 신규 Input System만, RPC는 `[Rpc(SendTo.…)]`만 쓴다.
- 새 `static Instance`, 매 프레임 `Find`/`Camera.main`/LINQ 할당, `async void`·새 코루틴을 만들지 마라.
- `.meta`를 직접 만들거나 고치지 말고, `.unity`·`.prefab`·`.asset`을 텍스트로 편집하지 마라.
- 씬·프리팹·SO 배선은 기존 설치 도구 패턴을 따라 **멱등 설치 + 검증 메뉴**로 만들어라.
  MCP 연결을 먼저 확인하고, 변경할 씬·에셋을 미리 고지하고, 저장 여부를 보고하라.
  **`GhostHunter > 프로토타입 게임 생성`으로 `Game` 씬을 재생성하지 마라** — 배치된 가구가 전부 사라진다.
  MCP가 없으면 수행할 배선을 번호로 안내하고 미실행으로 기록하라.

## 5. 완료 기준

기획서에 수용 기준 절이 없으므로 **아래를 완료 기준으로 삼되, 확정 규칙에서 그대로 유도한 것만
포함했다.** 새 게임 규칙을 여기서 만들지 마라.

| # | 시나리오 | 통과 조건 |
| --- | --- | --- |
| AC-1 | 드라이버 미장착·사망 상태에서 우클릭 | 분해·조립이 시작되지 않는다. 서버도 요청을 거절한다 |
| AC-2 | 분해 성공 | 큰 가구가 사라지고 부품이 전부 생성된다. 부품 내구도 = 원본 값. 아이템 내구도 5 감소 |
| AC-3 | 행동 중 이동·스킬·귀신 공격 | 즉시 중단, 처음부터 다시. **내구도는 감소하지 않는다.** 잠금·UI가 남지 않는다 |
| AC-4 | 내구도 ≤ 15 | 행동 시간이 9초. 행동 중 값이 바뀌어도 시작 시점 기준이 유지된다 |
| AC-5 | 조립 영역에 부품 일부만 | 실루엣 흰색, 조립 불가 |
| AC-6 | 다른 가구 부품 혼입 / 부품 개수 초과 | 실루엣 붉은색, 조립 불가 |
| AC-7 | 올바른 부품 전부, 바닥에 놓임 | 실루엣 초록색, 우클릭으로 조립 성공. 완성 가구 내구도 = 부품 평균(소수점 버림) |
| AC-8 | 서로 다른 같은 종류 가구에서 나온 부품 조합 | 출처를 구분하지 않고 조립된다 |
| AC-9 | 조립 중 부품 이탈·잡힘·다른 가구 진입 | 즉시 취소 |
| AC-10 | 잡혀 있던 가구를 분해 / 행동 중 사망·디스폰 | 홀더·물리·잠금·구독이 정리되고 예외가 나지 않는다 |
| AC-11 | 두 플레이어가 같은 대상에 동시 시도 | MD-9 확정대로 처리하고 중복 적용되지 않는다 |

## 6. 검증·문서·최종 보고

- **컴파일 → 관련 EditMode → PlayMode → Host/Client 수동 확인** 순으로 검증하라.
  에디터가 열려 있으면 MCP 경로부터 확인하고 **잠긴 프로젝트에 batchmode를 실행하지 마라.**
- 의미 있는 자동 검증에 집중하라. **조립 성립 판정(부품 집합 → 가능/불가·대상 가구)은 순수 로직으로
  분리해 EditMode로 촘촘히 덮어라** — 혼입·개수 초과·부분 집합·같은 종류 출처 혼합·빈 영역.
  내구도 평균·상속 계산도 순수 함수로 테스트하라. PlayMode는 서버 거절 케이스와 홀더 정리를 본다.
  구현을 그대로 베끼는 테스트는 피하라.
- 수동 검증은 Host·Client 양쪽에서 분해·조립을 수행하고, 상대 화면에 결과가 복제되는지 확인하라.
  Steam 2인 접속은 **PC 2대·계정 2개**에서만 검증 완료로 보고하라.
- 문서를 실제 구현과 맞춰라.
  - `docs/project/furniture-multidriver-system.md` — §7 대조 표와 §8 미결정 상태를 갱신하고,
    확정된 MD 항목은 확정값과 날짜를 남겨라. **확정되지 않은 항목을 확정처럼 쓰지 마라.**
  - `docs/architecture/furniture-multidriver.md`(신설) — 구성·흐름·권위·설치·검증을
    `docs/architecture/cleaning-system.md` 형식으로 쓴다.
  - `docs/project/roadmap.md` — **§1.6 FM 섹션을 신설**하고 FM-IMPL-1~4 상태를 관리하라.
  - `docs/README.md` 트리·요약·상태 표, `CLAUDE.md` §2 라우팅 행을 갱신하라.
  - 런타임 스폰 등 되돌리기 비싼 선택을 했다면 **ADR을 남겨라**(다음 번호 확인 후 작성).
- 완료 보고에는 구현 내용, 변경 경로, 확정/잔여 TBD, 실행한 검증 결과와 **미실행 항목 및 그 이유**,
  씬·프리팹·설정 저장 여부, 필요한 사용자 수동 작업을 적어라.
