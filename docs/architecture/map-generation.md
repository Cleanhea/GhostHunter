## 1. 시스템 개요

### 1.1 시스템 목적

맵 생성 시스템은 고정된 집 구조 안에서 방과 일부 오브젝트를 랜덤하게 구성하여 같은 맵을 반복 플레이하더라도 매 판 다른 공간 구성을 제공하고자 하는 시스템이다.

집 전체의 구조와 방의 위치, 이동 동선은 레벨 디자이너가 미리 제작한 형태를 그대로 사용하고자 한다. 이를 통해 플레이어의 이동 동선, 귀신 등장 연출, 추격 상황 등 주요 레벨 디자인을 의도한 형태로 유지한다.

대신 각 방에는 해당 방 카테고리에 맞는 여러 종류의 방 프리셋 중 하나가 랜덤으로 배치된다.

예를 들어 하나의 집이 아래와 같이 구성되어 있다고 가정해보자,

- 거실 1개
- 주방 1개
- 욕실 2개
- 침실 3개
- 창고 1

⇒ 각 침실 자리에는 준비된 프리셋 중 랜덤으로 선택되어 배치된다

ex)

```
침실 슬롯 1 → 침실 프리셋 B
침실 슬롯 2 → 침실 프리셋 E
침실 슬롯 3 → 침실 프리셋 A
```

따라서 집에서 플레이어가 전체적으로 이동할 수 있는 구조는 동일하지만, 실제 각 공간의 모습과 일부 플레이 환경은 매 판 달라지게 설계하고자 한다.

또한 방 내부의 벽, 문, 대형 가구 등 방의 기본적인 형태를 구성하는 요소는 각 방 프리셋에 고정하여 배치한다.

반면 쓰레기통, 쿠션, 박스, 협탁 등의 소형 오브젝트와 일부 게임 콘텐츠(귀신, 청소)는 방 내부에 지정된 위치 중 랜덤하게 생성하고자 한다.

> **목표 플레이 경험**
>
> 이를 통해 다음과 같은 플레이 경험을 제공하는 것을 목표로 한다.
>
> - 집 전체 구조는 고정이어서 익숙해질 수 있지만, 각 방의 내부 모습은 매 판 달라지게 하여 다른 판이라고 인식하게 한다.
> - 청소해야 하는 공간과 오브젝트의 구성이 달라진다.
> - 같은 집을 반복 플레이하더라도 탐색 과정에 일정 수준의 변화를 제공한다.
> - 고정 맵의 레벨 디자인 장점과 랜덤 생성의 반복 플레이성을 동시에 확보한다.

### 1.2 기획 피드백 — 규모·라운드 방향 (2026.09.05)

**① 밸런싱 손잡이는 맵 크기가 아니라 콘텐츠 밀도다.**

> 맵을 줄이지는 말고, 너무 루즈하다면 **청소할 가구를 줄이는 것**으로 해결책을 본다.

**② 프로토타입 수치에서 2배로 키워 1~2층을 구성한다.**

## 2. 맵 구성 구조

### 2.1 맵 구성 단위

#### House

하나의 집 전체를 House라고 정의하고자 함.

ex) `House_01`

#### Floor

House 내부의 한 층을 말함.

ex) `Floor_01` → 1층 / `Floor_02` → 2층 / `Floor_03` → 3층

> [구현 메모] **v0.3 신설 단위.** 현재 씬(`House_01`)에는 층 개념이 없다 — 바닥 슬래브 하나에
> 방을 평면으로 늘어놓은 단층 집이다. Floor 를 도입하면 생성 도구·슬롯 배치·귀신 배회 경계·
> 스폰 지점이 전부 층을 인자로 받아야 한다.

#### Room Slot & Room Pool

집 안에 어떤 종류의 방이 들어갈 지 미리 자리를 지정해놓은 것을 Slot이라고 정의하고자 함.

Bedroom의 3가지 버전을 만들었다고 가정한다면, 이 버전을 모아놓은 목록을 BedRoom Pool이라고 정의함.

예를 들어, 집에 침실이 3개 필요하다고 가정해보면

> **[House]**
>
> Bedroom Slot 01
> Bedroom Slot 02
> Bedroom Slot 03

이렇게 나타낼 수 있음. 즉 침실이 들어갈 자리 3개의 슬롯

Pool의 예시로는 침실로 사용할 수 있는 디자인이 5개 있다면

> **[Bedroom Pool]**
>
> - Bedroom_A
> - Bedroom_B
> - Bedroom_C
> - Bedroom_D
> - Bedroom_E

#### Room Preset

방의 기본 단위. ex) Bedroom_A, Bedroom_B, Bedroom_C

프리셋은 제작 후 그림으로 첨부할 예정.

#### Spawn Point

Spawn Point는 Room Preset 내부에서 랜덤 오브젝트 또는 게임 콘텐츠가 생성될 수 있는 위치를 미리 지정해 놓은 지점이다. ⇒ 자세한 내용은 [5. Spawn Point](#5-spawn-point)에서 설명한다.

폭은 전 층 **2.2m** — 문 폭(1.2~1.5m)보다 넓어 가구를 들고 오르내릴 수 있다(§10.2 B).
층마다 정렬돼 있으므로 계단실을 하나의 수직 코어로 만들 수 있다.

**② 배율을 곱하지 않는다.** 도면이 이미 20 × 16m 실측이다. 여기에 `MapScale` ×1.5를 곱하면
30 × 24m 가 되어 확정 치수를 벗어난다. **`MapScale` = 1.0** 이 산술적으로 강제된다.

**③ 그래서 방은 지금보다 작아진다.**

| | 현재 구현 | v0.3 도면 |
|---|---|---|
| 침실 슬롯 | 5.7 × 5.4m = 30.8㎡ | **4.2 × 4.0m = 16.8㎡** (−45%) |
| 가장 넓은 공간 | 거실 12.11 × 6.32m | 2층 갤러리 홀 8.4 × 6.4m / 1층 중앙 홀 6.8 × 6.8m |

방을 ×1.5로 넓혔던 이유(같은 가구를 더 넓은 방에서 던져 보기)는 **중앙 홀·갤러리 홀이 대신
맡는다.** 던지기 무대가 방에서 홀로 옮겨 가는 구조다.

**④ 대신 `Bedroom_B` 문제가 풀린다(MG-8 해결).** 프리셋 원본 치수는 A 3.8 × 3.6 / B 4.2 × 3.8 /
C 3.6 × 3.4m 인데, 도면의 침실 슬롯 **4.2 × 4.0m 는 셋을 모두 담는다.** ×1.5 슬롯에서
여백을 메우려고 넣었던 소품은 다시 빼야 한다.

**⑤ 도면 치수의 합은 외곽과 맞지 않는다.** v0.2 도면과 같은 성질이다(예: 2층 가로는
침실2 4.2 + 갤러리 홀 8.4 + 침실4 4.2 = 16.8m 로 20m 에 3.2m 모자란다). **외곽 20 × 16m 와
표의 방 치수를 고정값으로 잡고, 남는 몫은 홀·복도가 흡수한다** — 현재 생성 도구가 v0.2 에서
쓰던 방식 그대로다.

**⑥ 본문 §3.1 목록에 없는 공간이 도면에 있다** — 1층 **현관 2.8 × 2.4m**, 3층 **비밀 보관실
2.4 × 1.8m**, 그리고 집 밖 **앞마당·대문**. 비밀 보관실은 이름상 열쇠 해금(§1.2 ③)과 얽혀
보이지만 용도가 적혀 있지 않다 → [MG-17](#12-미결정-목록).

**⑦ 2층 갤러리 홀 한가운데가 오픈 보이드다.** 1층 중앙 홀과 수직으로 뚫려 있다. 2층에서 던진
가구가 1층으로 떨어지고, 1층에서 위를 올려다볼 수 있다 — 물리·귀신 시야·소리 판정이 층을
넘나든다 → [MG-16](#12-미결정-목록).

남는 면적을 가져가게 했다. 벽 두께는 0.18m, 좌표는 전부 벽 중심선 기준이다
(`Assets/Scripts/Editor/HousePrototypeBuilder.cs` 상단 상수).

### 평면 배율 (`HousePrototypeBuilder.MapScale`)

씬에 들어가는 집은 도면 **평면(X·Z)에만 ×1.5**를 먹인 크기다. 외곽 19.2 × 12.0m,
침실 슬롯 5.7 × 5.4m, 주방 7.40m 폭, 거실 12.11 × 6.32m. 같은 크기의 가구를 더 넓은 방에서
던져 보려고 넣은 값이다.

| 배율을 받는 것 | 배율을 받지 않는 것 |
|---|---|
| 벽 중심선 좌표, 방 크기, 바닥 슬래브, 걸레받이 길이 | 벽 높이 2.5m, 벽 두께 0.18m |
| 문·창·붙박이·계단의 **자리** | 문 폭(1.2 / 0.9 / 1.4 / 1.5m)과 높이 2.04m, 창 크기 |
| 조명 사거리·밝기(각 ×1.5) | 조명 높이, 붙박이·계단·가구 치수 |
| | 플레이어, 이동/점프, 투척 수치 |

- **트랜스폼 스케일은 쓰지 않는다.** 그룹에 스케일을 주면 개구부 폭과 벽 높이까지 같이 늘어난다.
  배율은 상수 정의부에서 **좌표에만** 곱한다 — `MapScale`이 붙은 상수가 평면 좌표,
  안 붙은 상수가 사람 기준 치수다.
- 개구부는 "자리 × 배율 + 원래 폭"으로 잡는다. 예: 침실 문은 칸막이 안쪽 면에서 0.2m 띄운
  자리에 폭 1.2m 그대로 뚫는다. 벽 조각의 끝점은 이 개구부에서 역산한다.
- 붙박이(주방 카운터·욕실)는 크기가 그대로라, 좌표를 방 안쪽 **면 기준**으로 잡아 벽을 따라간다.
- 생성 검증이 벽 높이 2.5m와 침실 문 1.2 × 2.04m를 직접 확인한다. 배율이 높이나 문으로
  새면 여기서 걸린다.
- 집이 평면 면적 기준 2.25배 넓어진 만큼 이동 시간이 늘고, 투척 사거리(조준 2m / 홀드 15m)가 상대적으로
  짧아진다. 체감이 나쁘면 `PlayerMoveSettings` · `FurnitureThrowSettings`를 따로 손본다.

**배율 비교용 집** — 배율이 정말 필요한지 눈으로 보려고, 같은 도면을 배율 없이(×1) 지은 집을
House_01 동쪽 3m 옆에 하나 더 세워 뒀다(`House_01_OriginalScale_Right`). 이 집은 방 슬롯도
프리셋도 쓰지 않고 **생성 도구가 방마다 가구를 깔아 준다** — 도면 치수에서 침실·주방·거실이
가구로 얼마나 차는지가 이 집의 전부이기 때문이다. 침실 두 칸은 도면의 Bedroom_A · Bedroom_C
구성을 그대로 쓴다. 자세한 것은 [06-furniture-physics.md](furniture-physics.md#씬-배치-prototype).

| 개구부 | 폭 | 위치 |
|---|---|---|
| 문 | 1.2m | 침실1, 침실2 |
| 문 | 0.9m | 욕실, 창고 |
| 실내 이동문 | 1.4m | 침실1 ↔ 주방 ↔ 침실2 연결부 |
| 현관문 | 1.5m | 거실 남측 |

도면 비고

- 모든 치수: 내부 실측 기준 (m)
- 표기 치수: 가로 × 세로, 높이
- 문 폭: 1.2m / 0.9m
- 실내 이동문: 1.4m
- 현관문: 1.5m

⇒ 같은 집에서는 방 프리셋 중복 금지.

> [구현 메모] 슬롯 수보다 프리셋이 많아야 성립한다. Floor_02 만 해도 침실 슬롯이 4개라
> Bedroom Pool 에 최소 5종이 필요하다(현재 3종) → [MG-13](#12-미결정-목록).
> `RoomSlotAssigner`는 풀이 슬롯보다 적으면 배정을 거부하고 에러를 남긴다.

### 3.4 계단 규칙

각 Floor는 계단을 통해 상하층과 연결한다.

추격 시 하나의 계단이 귀신에게 막히더라도 다른 경로를 사용할 수 있도록 주요 층에는
**계단 A와 계단 B의 두 개 이동 경로**를 배치한다.

> [구현 메모] 계단 폭·경사·형태(직선/꺾임)·계단참 유무는 원문에 없다
> → [MG-7](#12-미결정-목록). 가구를 들고 오르내릴 수 있어야 하므로(§10 B)
> 폭은 문 폭(1.2~1.5m)보다 넓어야 한다.

### 3.5 추격 동선 유지 규칙

Room Preset 랜덤 배치 후에도 House의 플레이어가 이동할 수 있는 **주요 이동 동선은 변경되지 않도록** 한다.

**중앙 홀, 복도, 계단 등 추격에 직접 영향을 주는 공간은 랜덤 생성하지 않고 고정**하고자 한다.

## 4. 방 프리셋 구성

방 안에 고정될 요소와 랜덤하게 나타낼 요소를 나누고자 한다.

### 4.1 고정 요소

- 집 전체 구조
- 집 전체 크기
- 각 방의 위치 및 용도
- 복도 및 방 연결 구조
- 출입구 및 문 위치
- 방 프리셋의 기본 구조
- 벽, 바닥, 창문
- 화장실 오브젝트 (ex_ 화장실: 변기, 세면대 등)

> [구현 메모] v0.2 의 마지막 항목은 "방을 구별할 수 있는 주요 대형 가구(ex_ 거실: 쇼파)"였다.
> v0.3 은 이를 **화장실 오브젝트**로 좁혔다. 침대·옷장 같은 대형 가구가 여전히 프리셋 고정인지,
> 랜덤 대상으로 넘어갔는지 원문만으로는 알 수 없다. 현재 구현은 **프리셋 고정**이다.

### 4.2 랜덤 요소

반복 플레이 시 공간의 변화를 제공할 수 있는 요소는 랜덤으로 결정하고자 함

- 각 Room Slot에 배치되는 Room Preset
- 소형 가구 및 소형 오브젝트
- 장식 및 잡동사니
- 청소 관련 콘텐츠 (ex_ 청소해야 할 가구, 물품들)
- 귀신 관련 콘텐츠

## 5. Spawn Point

Room Preset을 제작할 때 방 내부의 적절한 위치에 여러 개의 Spawn Point를 지정해놓고자 한다.

맵 생성 시 모든 Spawn Point에 오브젝트를 생성하는 것이 아니라, Spawn Point의 종류와 생성 조건에 따라 일부 지점만 선택하여 오브젝트를 생성한다.

예시: Bedroom_A

- 바닥 Spawn Point 6개 → 박스, 쓰레기통, 쓰레기봉투, 빨래바구니, 소형 가구
- 책상 위 Spawn Point 2개 → 컵, 책, 병, 휴지, 작은 소품 등
- 벽 Spawn Point 4개 → 액자, 거울, 불 스위치, 창문, 벽 장식 등
- 콘텐츠 Spawn Point → 청소 대상, 귀신 관련 오브젝트

맵 생성 시 위 Spawn Point 중 일부가 선택되며, 선택된 Spawn Point에 해당 종류의 오브젝트가 랜덤 생성된다.

### Spawn Point 선택 규칙

Room Preset에는 실제 생성할 오브젝트 수보다 많은 Spawn Point를 미리 배치하고, 맵 생성 시 각 Spawn Type별로 정해진 개수만큼 Spawn Point를 랜덤 선택한다.

선택되지 않은 Spawn Point에는 아무 오브젝트도 생성하지 않는다.

### 예시)

Bedroom_A의 바닥에 다음과 같이 Spawn Point가 배치되어 있다고 가정한다.

- Floor Spawn Point: 7개
- 실제 들어갈 오브젝트 개수: 3개

### Spawn Type별 개수 설정

Spawn Point 선택 개수는 Spawn Type마다 별도로 설정함.

| Spawn Type | 후보 Spawn Point | 실제 선택 수 |
|---|---|---|
| Floor | 6~7개 | 3개 |
| Desk | 2~3개 | 1개 |
| Sofa | 2~3개 | 1개 |
| Wall | 3~4개 | 1~2개 |

맵 생성 시:

```
Floor Spawn Point 7개 확인
↓
7개 중 서로 다른 Spawn Point 3개를 랜덤 선택
↓
선택된 각 Spawn Point에서 Floor Spawn Pool 조회
↓
Spawn Pool에서 오브젝트를 랜덤 선택
↓
선택된 3개의 위치에 각각 오브젝트 생성
```

결과 예시:

- Floor_01 → 이삿짐 박스
- Floor_04 → 쓰레기봉투
- Floor_06 → 빨래바구니

나머지 Floor_02 / 03 / 05 / 07에는 아무것도 생성하지 않는다.

또한, Bedroom이 생성될 때마다 6~7개의 후보 위치 중 서로 다른 3곳이 랜덤으로 선택되고, 해당 위치에 박스, 쓰레기봉투, 빨래바구니, 쓰레기통 등의 작은 오브젝트가 생성된다.

예:

```
1회차   Floor_01 / Floor_03 / Floor_06 선택
2회차   Floor_02 / Floor_04 / Floor_07 선택
3회차   Floor_01 / Floor_05 / Floor_07 선택
```

같은 Bedroom_A를 사용하더라도 작은 오브젝트가 놓이는 위치가 플레이마다 달라질 수 있다.

> **결정 (2026-09-05, 사용자 확정 — MG-14 해결): 후보 지점에 미리 배치한다.**
> 런타임에 프리팹을 `Spawn()` 하지 않는다 → [ADR-0009](decisions/ADR-0009-scene-placed-level-objects.md) 유지.
>
> [구현 메모] **"선택되지 않은 것을 어떻게 치우느냐"가 남는다.** 씬에 놓인 `NetworkObject` 를
> 비활성화하는 방식은 NGO 스폰 경로와 얽혀 있어 검증 없이 쓰면 안 된다. 안전한 길은 이미
> 검증된 방 프리셋과 **같은 방식** — 집 밖 보관 자리에 두고 **뽑힌 것만 서버가 후보 지점으로
> 옮긴다**(`RoomPreset.ApplyTo` 패턴). 클라이언트는 `NetworkTransform` 복제로 같은 결과를 보고,
> 늦게 들어와도 어긋나지 않는다.

### 5.1 방 내부 오브젝트 결정 프로세스

**방 내부 오브젝트 결정**

예시)

```
Bedroom_B

Floor Spawn 01
      ↓
Floor Object Pool
      ↓
박스 선택

Sofa Spawn 01
      ↓
Sofa Object Pool
      ↓

```

## 6. 콘텐츠 배치 시스템

일반 오브젝트와 게임 콘텐츠 분리

ex) 청소 대상, 귀신 관련 오브젝트, 은신용 요소, 필요한 물건 등 콘텐츠에 필요한 오브젝트는 일반 오브젝트와 분리해야 함.

### 6.1 Work Room 선정

House 내부의 **모든 Room이 작업 대상이 되는 것은 아니다.**

게임 시작 시 전체 Room 중 일부를 `Work Room`으로 랜덤 선정한다.

- Work Room으로 선정된 방에만 **청소 대상 및 이삿짐 콘텐츠를 생성**한다.
- Work Room으로 선정되지 않은 방도 플레이어와 귀신이 이동할 수 있으며 **추격 및 회피 공간**으로 사용한다.

**임시값:** 전체 방 12~15개 / Work Room 6~8개

즉, 치워야 하는 가구·오브젝트를 **20~25개** 두려고 함.

> [구현 메모] 이 세 수치가 **§1.2 ①의 밸런싱 손잡이**다. 플레이가 늘어지면 맵이 아니라
> 이 값을 먼저 내린다.
>
> **"전체 방 12~15개"는 1~2층 기준이다(MG-5 해결).** 도면 실측으로 1층 7 + 2층 8 = **15개**,
> 다락 6개는 열쇠 해금 공간이라 별도다. Work Room 6~8개는 그 15개 중에서 뽑는다.
>
> - 다락이 열리면 Work Room 후보가 21개로 늘어나는지, 다락은 작업 대상에서 빼는지는 미정이다.
> - v0.2 의 "청소 대상은 각 방에 최소 2개 이상 존재해야 한다"는 v0.3 원문에서 사라졌다.
>   Work Room 6~8개에 20~25개면 방당 평균 3~4개다 → [MG-6](#12-미결정-목록).

### 6.2 Content Spawn Point

한 집에는 콘텐츠(ex_귀신 집착 오브젝트)가 반드시 **1~3개** 생성된다.

해당 오브젝트는 Content Spawn Point 중 하나에 생성된다.

### 6.3 콘텐츠 생성 제한

> **미결정:** 원문에서 항목만 있고 내용은 아직 작성되지 않았다(v0.2·v0.3 모두)
> → [MG-10](#12-미결정-목록).

### 6.4 게임 콘텐츠 결정 프로세스

**게임 콘텐츠 결정**

일반 인테리어 오브젝트 배치가 완료된 후 청소 및 귀신 등 실제 플레이에 필요한 콘텐츠를 생성한다.

```
완성된 Room
↓
Content Spawn Point 확인
↓
콘텐츠 생성 조건 확인
↓
청소 / 귀신 / 특수 콘텐츠 배치
↓
검증
```

최종적으로 다음과 같은 계층으로 맵이 생성된다.

```
House
│
├─ Room Slot
│    │
│    └─ Room Preset
│          │
│          ├─ Fixed Object
│          │
│          ├─ Spawn Point
│          │     │
│          │     └─ Random Object
│          │
│          └─ Content Spawn Point
│                │
│                └─ Game Content
│
├─ Room Slot
│    └─ Room Preset
│          └─ ...
│
└─ Room Slot
     └─ Room Preset
          └─ ...
```

## 8. 생성 제한 / 충돌 규칙

> 🚨 이런 결과는 절대 나오면 안 되는 것을 싹 다 적고자 함.

1. 문 앞 일정 범위에는 랜덤 오브젝트를 생성하지 않는다.
2. 플레이어의 필수 이동 경로를 완전히 막는 오브젝트는 허용하지 않는다.
3. 은신이 가능한 가구가 최소 1개 이상 존재하도록 방을 조합한다.
4. 오브젝트가 생성된 자리에 다른 오브젝트가 겹쳐 생성되지 않도록 한다.
5. **계단 A/B 앞 일정 범위에는 오브젝트를 생성하지 않는다.**
6. **중앙 홀 및 주 이동 동선을 막는 오브젝트를 생성하지 않는다.**
7. **각 층에는 최소 1개의 순환 가능한 이동 경로가 유지되어야 한다.**
8. **모든 주요 공간에서 최소 2개 이상의 이동 방향을 확보하는 것을 권장한다.**
9. **두 계단으로 향하는 경로가 동시에 오브젝트에 의해 차단되면 안 된다.**
10. **Work Room이 특정 층에 지나치게 몰리지 않도록 한다.**

⇒ 해당 조건을 지키지 못한 경우 **해당 방을 다시 추첨**

> [구현 메모] 재추첨의 **횟수 상한과 실패 시 폴백**이 없다 → [MG-12](#12-미결정-목록).
> 현재 구현은 규칙 1(문 앞)·4(겹침)에 해당하는 것만 에디터 검증으로 막는다
> (`HousePrototypeBuilder.ValidateRoomPresets` — 프리셋 × 슬롯 전 조합의 벽·가구 겹침과 문짝 스윕).
> 규칙 10의 "지나치게"는 정량 기준이 필요하다.

**Spawn Point 자리는 소품 큐브로 미리 채워 두었다** — 랜덤 선택 로직은 아직 없으므로, 프리셋마다
바닥 Spawn Point 자리(상자 · 쓰레기통 · 빨래바구니)와 책상/협탁 위 Spawn Point 자리(컵 · 책 ·
화장품 상자)에 소품을 **고정으로** 놓았다. 10장 표대로 실제 메시 대신 큐브 하나로 때운 것이고,
전부 던질 수 있는 물리 가구다. 나중에 Spawn Point 시스템이 들어오면 이 좌표가 그대로
후보 지점이 된다. 위에 얹는 소품은 상판 윗면을 지지면 높이로 넘겨 정확히 앉힌다
(`MakePhysical(..., supportHeight)`) — 몇 cm 떠 있으면 세션 시작과 동시에 떨어진다.

**가구 원본** — 프리셋에 놓인 가구는 전부 `Assets/Prefabs/Furniture/` 프리팹의 인스턴스다
(MIG-6, 2026-08-31 커밋 `015f874` 로 가구 33종·문 3종을 실제로 구웠다 — `Game.unity` 에
`PrefabInstance` 108건). 같은 종류는 어느 방에 있든 같은 프리팹에서 나오므로, 치수를 고치려면
프리팹만 고치면 된다. 벽 방향이 다른 자리는 치수가 아니라 회전으로 맞춘다.

**배치 방식** — 프리셋을 프리팹으로 스폰하지 않는다. 맵 가구는 전부 씬에 놓인 `NetworkObject`라
호스트가 시작될 때 한꺼번에 스폰되는데, 프리셋을 프리팹으로 만들면 가구가 중첩 NetworkObject가
되고 스폰 경로가 둘로 갈린다. 대신 **이미 스폰된 가구를 서버가 슬롯으로 옮긴다**
(`RoomPreset.ApplyTo`). 클라이언트는 `NetworkTransform` 복제로 같은 결과를 보고, 늦게 들어와도
스폰 시점의 위치를 그대로 받으므로 "어떤 프리셋이 뽑혔는지"를 따로 동기화할 필요가 없다.

**중복 없음** — 풀을 Fisher-Yates로 섞어 앞에서부터 슬롯에 하나씩 준다. A·A 같은 조합은 나오지
않는다. 슬롯 수보다 프리셋이 적으면 배정 자체가 불가능하므로 생성 검증이 막는다.
세션을 다시 시작하면 먼저 모든 프리셋을 전시 자리로 되돌린 뒤 다시 뽑는다.

**문 동선 제약** — 침실1의 문은 방 서쪽 끝에서 4.3m(동쪽 칸막이 쪽), 침실2의 문은 0.72m
지점에 있다(도면의 L자 외곽과 욕실 위치 때문에 두 슬롯의 문 위치를 맞출 수 없다). 어느 슬롯에
뽑혀도 문이 가구를 쓸고 지나가지 않도록, 프리셋은 **방 남쪽 1.11m 띠를 비운다**(문짝 1.2m가
그리는 사분원). 예외는 두 문 사이 가운데 띠(방 중심 기준 x −0.93 ~ +1.45)로, 어느 문도
지나가지 않아 남쪽 벽까지 쓸 수 있다 — Bedroom_C의 상자가 여기 있다. 전시장 바닥에 이 금지
구역을 어두운 띠로 깔아 뒀다(`DoorSweep_KeepOut`).

**도면과 달라진 점** — 슬롯은 5.7 × 5.4m이며 세 프리셋 모두 도면의 핵심 가구 구성을
그대로 담는다(B의 서랍장·발치 협탁 포함). ×2 방의 빈 공간을 채우려고 넣었던 추가 가구 2개씩은
×1.5 축소 시 서로 겹쳐 제거했다. 방의 성격(A 1인용 침실 / B 부부 침실 / C 아이 방)은 유지하고,
남은 여백은 위의 고정 배치 소품이 메운다. 바닥 소품은 두 침실 모두의 문짝을 피하는 남쪽 가운데
안전 띠에 모아 둔다.

> [구현 메모] 피드백 ②로 평면 배율을 다시 올리면 **2026-08-23 축소 때 제거한 여백이 되돌아온다.**
> 그때는 가구를 더 넣어 메웠지만, 이번에는 §5 Spawn Point 시스템이 그 자리를 메우는 편이 맞다 —
> 여백은 소품 후보 지점이 되고, 방마다 뽑히는 소품이 달라진다.

프리셋 가구를 늘릴 때 지켜야 할 것:

- 남쪽 1.11m 띠는 그대로 비운다(두 문 사이 가운데 띠 x −0.93 ~ +1.45 제외).
- 북쪽 벽 가운데 창(폭 1.45m, 방 중심 기준 x ±0.725)은 키 큰 가구로 막지 않는다.
- 검증이 프리셋 × 슬롯 전 조합을 실제로 놓아 보므로, 겹치면 생성 단계에서 걸린다.

**생성 검증** — `HousePrototypeBuilder.ValidateRoomPresets`가 프리셋 × 슬롯 **전 조합**을 실제로
배치해 보고 (1) 벽·가구 겹침 (2) 문짝이 닫힘~열림 사이 어느 각도에서도 가구를 쓸지 않는지를

메뉴를 실행해 `Game.unity`에 저장하지 못했다. 따라서 위 루트의 실제 생성·씬 저장·수동 Play 이동은 **확인 필요**다.

EditMode batchmode도 시도했지만, Unity Licensing Client 초기화 단계에서 종료되어 결과 XML이 생성되지 않았다
(복제 환경 차단, 테스트 케이스 **0건 실행**). 이 결과로 생성기 동작을 판정하지 않는다.
실행 순서는 `Game.unity`를 연 뒤 `GhostHunter > 맵 B·C 프로토타입 추가 (실내·계단·가구)`를 한 번
실행하고, Console의 검증 통과/NGO 해시 로그를 확인하는 것이다. 생성 후 `GhostHunter > 맵 B·C 프로토타입 검증`을
다시 실행한다. Player의 CharacterController와 전역 밸런스 설정은 바꾸지 않는다.

#### C. 원문의 서술형 확인 항목

**1. Room 랜덤 선택이 제대로 되는가**

침실 슬롯 3개가 있다면:

```
1회
Bedroom A / C / D

2회
Bedroom B / D / A

3회
Bedroom C / A / B
```

처럼 의도한 규칙대로 뽑히는지.

**2. Spawn Point 방식이 실제로 편한가**

기획 단계에서는 Spawn Point가 좋아 보여도 직접 몇 개 만들어보면

> "어? 책상 위 / 바닥 / 벽 이렇게 나누니까 너무 많은데?"

또는 반대로

> "Floor 하나로 묶으니까 이상한 배치가 너무 많이 나오네."

같은 문제가 나올 수 있음.

**3. Object Pool 구조가 적절한가**

예를 들어 처음에는

```
Floor Object Pool
```

하나면 될 것 같았는데 테스트하다 보면

```
Floor_Corner
Floor_Open
BedSide
TableTop
Shelf
```

처럼 세분화할 필요가 있다는 걸 알 수도 있어.

**4. 재생성했을 때 충분히 달라 보이는가**

이게 아주 중요함.

기획상으로는

> 방 랜덤 + 소형 오브젝트 랜덤 = 매 판 다른 느낌

이라고 생각했는데 직접 20번 생성해보니까

> "별 차이 없는데?"

가 될 수도 있거든.

그럼 프리셋 종류를 늘리거나 랜덤 요소를 더 추가해야 한다는 걸 일찍 알 수 있어.
