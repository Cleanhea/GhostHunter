## 1. 시스템 개요

### 1.1 시스템 목적

맵 생성 시스템은 고정된 집 구조 안에서 방과 일부 오브젝트를 랜덤하게 구성하여 같은 맵을 반복 플레이하더라도 매 판 다른 공간 구성을 제공하고자 하는 시스템이다.

집 전체의 구조와 방의 위치, 이동 동선은 레벨 디자이너가 미리 제작한 형태를 그대로 사용하고자 한다. 이를 통해 플레이어의 이동 동선, 귀신 등장 연출, 추격 상황 등 주요 레벨 디자인을 의도한 형태로 유지한다.

대신 각 방에는 해당 방 카테고리에 맞는 여러 종류의 방 프리셋 중 하나가 랜덤으로 배치된다.

시스템 요약:

- 맵 전체 구조는 고정
- 각 Room Slot에 Room Preset 랜덤 배치
- 일부 오브젝트는 Spawn Point 기반 랜덤 생성
- 생성 결과가 조건을 위반하면 해당 단계 재선정

### 1.2 기획 피드백 — 규모·라운드 방향 (2026.09.05)

v0.3과 함께 전달된 피드백 및 사용자 결정 기록이다. **작업량·생성 절차는 최신 v0.4를 따른다.**
아래 규모·라운드·스페셜 공간 결정은 이번 첨부가 새 값을 제시하지 않아 기존 기록으로 보존한다.

**① 밸런싱 손잡이는 맵 크기가 아니라 콘텐츠 밀도다.**

> 맵을 줄이지는 말고, 너무 루즈하다면 **청소할 가구를 줄이는 것**으로 해결책을 본다.

플레이가 늘어지면 먼저 **Target Furniture Type 수와 Type별 Target Furniture Count**를 조절한다
(§6). v0.4에서는 B·C안의 이동 시간·도주 공간과 작업량을 함께 검증한다(§10.2).

**② 프로토타입 수치에서 2배로 키워 1~2층을 구성한다.**

> **결정 (2026-09-05, 사용자 확정 — MG-2 해결)**
>
> - 한 층 **20 × 16m**, **2개 층** + 다락 **14 × 10m**. 당시 v0.3 §10의 값이며, 현재 비교 기준인 **A안**이다.
> - **방을 부풀리지 않는다.** 피드백의 "2배"는 **방이 아니라 집 전체**(층수·방 개수)를 키우는
>   뜻으로 확정한다. 연면적 230㎡ → **780㎡ (3.4배)** 로 체감은 충족된다.
> - **`MapScale` = 1.0.** 층별 도면이 이미 20 × 16m **실측**이라 배율을 곱할 자리가 없다.
>   침실 슬롯은 도면값 **4.2 × 4.0m** 다 — 현재 5.7 × 5.4m 보다 **작아진다**(§2 도면 ③).
>
> 근거: 방 크기까지 ×2(슬롯 7.6 × 7.2 = 54.7㎡)로 하면 층당 8~9개 공간이 320㎡ 에 들어가지
> 않는다(침실 4개만으로 219㎡). 도면이 그린 4.2 × 4.0m 슬롯이라야 8~9칸이 실제로 들어간다.

**③ 3층 다락방과 지하실은 열쇠로 여는 스페셜 공간이다.**

일반 층과 달리 처음부터 열려 있지 않다. **열쇠를 찾아야 열리고**, 그만큼 난이도가 높다.
열쇠의 스폰 규칙·개수·사용 방식은 미정 → [MG-15](#12-미결정-목록).

## 2. 맵 구성 구조

### 2.1 맵 구성 단위

v0.4 용어 정의:

| 용어 | 정의 |
|---|---|
| House | 하나의 맵 전체 |
| Floor | House 내부의 한 층 |
| Room Slot | 특정 종류의 Room이 배치될 위치 |
| Room Pool | 동일 Category의 Room Preset 목록 |
| Room Preset | 실제 배치되는 방 프리셋 |
| Spawn Point | 랜덤 Object 생성 후보 위치 |
| Target Furniture Type | 이번 게임에서 플레이어가 운반해야 할 가구 종류 |
| Target Furniture Count | 해당 종류의 가구 개수 (`Target Count`로도 표기) |

아래 예시·도면 설명은 이전에 수령한 자료와 구현 컨텍스트다.

#### House

하나의 맵 전체를 House라고 정의한다.

ex) `House_01`

#### Floor

House 내부의 한 층을 말함.

ex) `Floor_01` → 1층 / `Floor_02` → 2층 / `Floor_03` → 3층

> [구현 메모] **v0.3 신설 단위.** 현재 씬(`House_01`)에는 층 개념이 없다 — 바닥 슬래브 하나에
> 방을 평면으로 늘어놓은 단층 집이다. Floor 를 도입하면 생성 도구·슬롯 배치·귀신 배회 경계·
> 스폰 지점이 전부 층을 인자로 받아야 한다.

#### Room Slot & Room Pool

집 안에 어떤 종류의 방이 들어갈 지 미리 자리를 지정해놓은 것을 Slot이라고 정의하고자 함.

Bedroom의 3가지 버전을 만들었다고 가정한다면, 이 버전을 모아놓은 목록을 BedRoom Pool이라고 정의함.

예를 들어, 집에 침실이 3개 필요하다고 가정해보면

> **[House]**
>
> Bedroom Slot 01
> Bedroom Slot 02
> Bedroom Slot 03

이렇게 나타낼 수 있음. 즉 침실이 들어갈 자리 3개의 슬롯

Pool의 예시로는 침실로 사용할 수 있는 디자인이 5개 있다면

> **[Bedroom Pool]**
>
> - Bedroom_A
> - Bedroom_B
> - Bedroom_C
> - Bedroom_D
> - Bedroom_E

#### Room Preset

방의 기본 단위. ex) Bedroom_A, Bedroom_B, Bedroom_C

프리셋은 제작 후 그림으로 첨부할 예정.

#### Spawn Point

Spawn Point는 Room Preset 내부에서 랜덤 오브젝트 또는 게임 콘텐츠가 생성될 수 있는 위치를 미리 지정해 놓은 지점이다. ⇒ 자세한 내용은 [5. Spawn Point](#5-spawn-point)에서 설명한다.

### 2.2 데이터 구조

```text
House
└─ Floor
   └─ Room Slot
      └─ Room Preset
         ├─ Fixed Object
         └─ Spawn Point
            └─ Random Object
```

> [구현 메모] 이 트리는 기획상의 포함 관계다. 현재 씬에서는 `RoomPreset.ApplyTo`가 이미 배치된
> 가구를 이동하며, 트리를 그대로 중첩 `NetworkObject` 구조로 만드는 것은 아니다(§10.1).

#### 도면에서 읽어 낸 것 [구현 메모]

**① 계단은 세 층에서 같은 자리다.** 계단 A·B 모두 북쪽 중앙, 욕실을 사이에 두고 좌우.
폭은 전 층 **2.2m** — 문 폭(1.2~1.5m)보다 넓어 가구를 들고 오르내릴 수 있다(§10.2 B).
층마다 정렬돼 있으므로 계단실을 하나의 수직 코어로 만들 수 있다.

**② 배율을 곱하지 않는다.** 도면이 이미 20 × 16m 실측이다. 여기에 `MapScale` ×1.5를 곱하면
30 × 24m 가 되어 확정 치수를 벗어난다. **`MapScale` = 1.0** 이 산술적으로 강제된다.

**③ 그래서 방은 지금보다 작아진다.**

| | 현재 구현 | v0.3 도면 |
|---|---|---|
| 침실 슬롯 | 5.7 × 5.4m = 30.8㎡ | **4.2 × 4.0m = 16.8㎡** (−45%) |
| 가장 넓은 공간 | 거실 12.11 × 6.32m | 2층 갤러리 홀 8.4 × 6.4m / 1층 중앙 홀 6.8 × 6.8m |

방을 ×1.5로 넓혔던 이유(같은 가구를 더 넓은 방에서 던져 보기)는 **중앙 홀·갤러리 홀이 대신
맡는다.** 던지기 무대가 방에서 홀로 옮겨 가는 구조다.

**④ 대신 `Bedroom_B` 문제가 풀린다(MG-8 해결).** 프리셋 원본 치수는 A 3.8 × 3.6 / B 4.2 × 3.8 /
C 3.6 × 3.4m 인데, 도면의 침실 슬롯 **4.2 × 4.0m 는 셋을 모두 담는다.** ×1.5 슬롯에서
여백을 메우려고 넣었던 소품은 다시 빼야 한다.

**⑤ 도면 치수의 합은 외곽과 맞지 않는다.** v0.2 도면과 같은 성질이다(예: 2층 가로는
침실2 4.2 + 갤러리 홀 8.4 + 침실4 4.2 = 16.8m 로 20m 에 3.2m 모자란다). **외곽 20 × 16m 와
표의 방 치수를 고정값으로 잡고, 남는 몫은 홀·복도가 흡수한다** — 현재 생성 도구가 v0.2 에서
쓰던 방식 그대로다.

**⑥ 본문 §3.1 목록에 없는 공간이 도면에 있다** — 1층 **현관 2.8 × 2.4m**, 3층 **비밀 보관실
2.4 × 1.8m**, 그리고 집 밖 **앞마당·대문**. 비밀 보관실은 이름상 열쇠 해금(§1.2 ③)과 얽혀
보이지만 용도가 적혀 있지 않다 → [MG-17](#12-미결정-목록).

**⑦ 2층 갤러리 홀 한가운데가 오픈 보이드다.** 1층 중앙 홀과 수직으로 뚫려 있다. 2층에서 던진
가구가 1층으로 떨어지고, 1층에서 위를 올려다볼 수 있다 — 물리·귀신 시야·소리 판정이 층을
넘나든다 → [MG-16](#12-미결정-목록).

#### B·C안 적용된 실내 좌표 — 여백 정리 재설계 (2026-09-06, 씬 반영 완료) [구현 메모]

위 두 표(B안·C안)의 방 치수는 **원본 손그림 도면(HousePlanB.png·HousePlanC.png)의 값 그대로**다.
도면 자체가 "방 치수의 합"과 "외곽 치수"가 맞지 않는 축소 스케치라서, 그 차이가 방-홀 사이
미배정 통로(최대 5.25m), 외벽 뒤 사용 안 되는 띠(최대 3.9m), 같은 날개 안에 쌓인 방 사이
목적 없는 틈(최대 6.0m)으로 남아 있었다 — 6개 층 전체에서 방+홀이 차지하는 비율이 층당
36~53%에 불과했다.

**`PlanVariantPrototypeSetup.cs`의 `CreatePlanB()`/`CreatePlanC()`에 실제로 들어간 좌표는 이 표와
다르다.** 원본 도면 값을 고정 상수로 두고 남는 폭은 방 확장으로 흡수하도록 재설계했다. 정확한
좌표(방마다 4자리 소수)는 코드의 `Room(...)` 호출과 그 위 주석을 참고한다 — 이 문서는 방식과
결과만 요약한다.

**적용 원칙**

1. 문이 없는 방향으로 외벽까지 여백이 있으면 벽 안쪽 면까지 확장한다(`WallThickness` 0.18m
   전체를 외곽선에서 뺀 값이 한계— Unity `ValidateRoomBounds`가 절반이 아니라 전체 두께를
   요구한다는 점을 씬 반영 중 직접 확인했다. float 반올림 여유로 0.02m를 추가로 더 뺀다).
2. **같은 날개 안에서 쌓인 방 사이 간격을 완전히 없앤다.** 날개가 걸치는 구간(외벽↔외벽, 또는
   외벽↔남측 방 열 경계)을 정하고, 각 방의 원래 도면 깊이 비율대로 빈틈없이 나눠 모든 방이
   서로 벽을 맞대게 한다 — 균등 분배가 아니라 원래 컸던 방(거실·식당·침실)이 더 많이 가져간다.
3. 날개↔홀 간격은 2층 침실 측면만 도면 확정값(B 2.3m·C 2.5m)을 그대로 쓰고, 나머지(1층·다락)는
   기존 간격을 절반으로 줄이되 1.2~3.0m 범위로 맞춘다.
4. 중앙 홀·갤러리·현관·계단은 손대지 않는다(치수 고정값이거나 MG-7 대기 [TEMP] 값).

#### 규모가 바뀌면 딸려 오는 것 [구현 메모]

**규모 변경 영향의 비교 기록이다.** 현재 제작 기준은 B안(MG-20)이며, 아래 비교 자체가
밸런스 수치 변경을 확정하지 않는다. 원본 도면 기준 계산과 현재 여백 정리 실내 치수도 구분한다.

**① 침실 프리셋의 여백 문제가 되돌아온다.** 프리셋 원본은 A 3.8 × 3.6 / B 4.2 × 3.8 /
C 3.6 × 3.4m 다.

| 슬롯 | 가장 큰 프리셋(4.2 × 3.8) 대비 남는 여백 |
|---|---|
| A안 4.2 × 4.0m | 0 × 0.2m — **딱 맞는다** (MG-8 해결의 근거) |
| B안 6.0 × 5.5m | 1.8 × 1.7m |
| C안 7.5 × 7.0m | 3.3 × 3.2m |

A안의 슬롯은 MG-8 치수 초과 문제를 해소한다. B·C안은 여백이 더 커지므로 프리셋을 다시
구성할지, 여백을 유지할지, 소품을 배치할지 검토해야 한다. 도면만으로 가구 추가를 결정하지 않는다.

**② 반대로 B안은 현재 구현과 방 크기가 거의 같다.** 지금 씬의 침실 슬롯은 5.7 × 5.4m = 30.8㎡ 이고
B안은 6.0 × 5.5m = 33.0㎡ 다. 침실 면적은 비슷하지만 홀·복도·층수가 달라
**같은 플레이 체감이라고 단정할 수 없다.** A안의 침실 면적은 현재보다 약 45% 작다.

**③ 귀신 탐지의 상대적 범위가 달라진다.** 같은 탐지 반경을 유지하면 집이 커질수록 집 크기 대비
범위가 작아진다. 실제 영향은 벽·방 배치와 함께 플레이로 확인한다.
탐지 수치의 근거는 [ghost-system.md](../project/ghost-system.md)에 두고 이 도면 반영으로 바꾸지 않는다.

**④ 이동 거리.** 1층 장변은 A안 20m / B안 30m / C안 40m로, B·C안은 각각 1.5배·2배다.
실제 횡단 시간은 문·복도를 우회하는 경로와 이동 설정에 따라 달라진다.

**⑤ 채택 시 그레이박스 치수·배치를 갱신해야 한다.** 이미 세운 `House_01_V03_Graybox_Right`는
20 × 16m 기준이다. 이번 문서 작업에는 재생성을 포함하지 않는다 → [roadmap MAP-1·MAP-2](../project/roadmap.md).

**⑥ 층고·굴착 도약(MAP-12)은 이 결정과 무관하다** — 평면만 커지고 벽 높이는 도면에 없다.

**⑦ 계단 폭이 B·C안 도면에 표기되지 않았다.** A안만 2.2m 로 적혀 있다. 복도 폭(B 2.8 / C 3.0)이
계단실 폭과 같은지 확인이 필요하다 → MG-7 과 함께 남는다.

### 평면 배율 (`HousePrototypeBuilder.MapScale`)

씬에 들어가는 집은 도면 **평면(X·Z)에만 ×1.5**를 먹인 크기다. 외곽 19.2 × 12.0m,
침실 슬롯 5.7 × 5.4m, 주방 7.40m 폭, 거실 12.11 × 6.32m. 같은 크기의 가구를 더 넓은 방에서
던져 보려고 넣은 값이다.

| 배율을 받는 것 | 배율을 받지 않는 것 |
|---|---|
| 벽 중심선 좌표, 방 크기, 바닥 슬래브, 걸레받이 길이 | 벽 높이 2.5m, 벽 두께 0.18m |
| 문·창·붙박이·계단의 **자리** | 문 폭(1.2 / 0.9 / 1.4 / 1.5m)과 높이 2.04m, 창 크기 |
| 조명 사거리·밝기(각 ×1.5) | 조명 높이, 붙박이·계단·가구 치수 |
| | 플레이어, 이동/점프, 투척 수치 |

- **트랜스폼 스케일은 쓰지 않는다.** 그룹에 스케일을 주면 개구부 폭과 벽 높이까지 같이 늘어난다.
  배율은 상수 정의부에서 **좌표에만** 곱한다 — `MapScale`이 붙은 상수가 평면 좌표,
  안 붙은 상수가 사람 기준 치수다.
- 개구부는 "자리 × 배율 + 원래 폭"으로 잡는다. 예: 침실 문은 칸막이 안쪽 면에서 0.2m 띄운
  자리에 폭 1.2m 그대로 뚫는다. 벽 조각의 끝점은 이 개구부에서 역산한다.
- 붙박이(주방 카운터·욕실)는 크기가 그대로라, 좌표를 방 안쪽 **면 기준**으로 잡아 벽을 따라간다.
- 생성 검증이 벽 높이 2.5m와 침실 문 1.2 × 2.04m를 직접 확인한다. 배율이 높이나 문으로
  새면 여기서 걸린다.
- 집이 평면 면적 기준 2.25배 넓어진 만큼 이동 시간이 늘고, 투척 사거리(조준 2m / 홀드 15m)가 상대적으로
  짧아진다. 체감이 나쁘면 `PlayerMoveSettings` · `FurnitureThrowSettings`를 따로 손본다.

**배율 비교용 집** — 배율이 정말 필요한지 눈으로 보려고, 같은 도면을 배율 없이(×1) 지은 집을
House_01 동쪽 3m 옆에 하나 더 세워 뒀다(`House_01_OriginalScale_Right`). 이 집은 방 슬롯도
프리셋도 쓰지 않고 **생성 도구가 방마다 가구를 깔아 준다** — 도면 치수에서 침실·주방·거실이
가구로 얼마나 차는지가 이 집의 전부이기 때문이다. 침실 두 칸은 도면의 Bedroom_A · Bedroom_C
구성을 그대로 쓴다. 자세한 것은 [06-furniture-physics.md](furniture-physics.md#씬-배치-prototype).

| 개구부 | 폭 | 위치 |

## 3. 집 구성·동선 참고 [구현 메모]

기존 v0.3 도면과 사용자 결정에서 가져온 집 구성 기록이다. 최신 고정·랜덤 구분은 §4,
Room Preset 선택은 §4.2, 생성 순서·실패 처리는 §7·§8을 따른다.

### 3.1 집 하나 당 기본 구성

맵은 **2~3층 규모의 대저택**을 기준으로 하며, 각 층의 전체 구조와 주요 이동 동선은 고정한다.
각 층 내부의 Room Slot에는 해당 카테고리의 Room Preset을 랜덤 배치한다.

맵 생성 시스템을 통해 귀신 추격 상황에서 사용할 수 있는 이동 동선과 층간 이동 경로가 유지되도록 하고자 한다.

작업 대상 선정은 v0.4의 **Target Furniture Type·Count**를 따른다(§6).
이전의 작업 대상 방 선정 규칙은 최신 생성 절차에 명시되지 않았다(MG-6).

> **House_01**
>
> **Floor_01**
> - 중앙 홀
> - 거실
> - 식당
> - 주방
> - 서재
> - 욕실
> - 세탁실/유틸리티
> - 창고
>
> **Floor_02**
> - 중앙 갤러리 홀
> - 침실 ×4
> - 가족실
> - 서재/작업실
> - 욕실 ×2
>
> **Floor_03**
> - 다락 거실
> - 게스트룸 ×2
> - 놀이방
> - 창고방
> - 작은 욕실

초기 프로토타입에서는 **House_01 한 종류만 제작하여 검증한다.**
이후 동일한 시스템을 사용하여 다른 Mansion Layout을 추가할 수 있다.

> [구현 메모] **v0.2의 "House 1/2/3 세 종류" 계획은 이 절로 대체됐다.** 참고로 v0.2 구성은
> House 1(거실1·주방1·욕실1·침실2·창고1) / House 2(욕실2·침실3) / House 3(지하실1) 이었고,
> 현재 씬의 `House_01`이 그중 House 1 이다.
>
> **도면(2026-09-05)과 대조한 실제 구성**은 아래와 같다. 본문 목록과 두 군데 다르다.
>
> | 층 | 방 (홀·계단·현관 제외) | 개수 |
> |---|---|---|
> | Floor_01 | 서재 · 욕실 · 세탁실/유틸리티 · 창고 · 거실 · 식당 · 주방 | **7** |
> | Floor_02 | 침실 ×4 · 욕실 ×2 · 가족실 · 서재/작업실 | **8** |
> | Floor_03 | 게스트룸 ×2 · 놀이방 · 창고방 · 작은 욕실 · **비밀 보관실** | **6** |

> 도면에도 아직 없다 → [MG-18](#12-미결정-목록).

### 3.2 Room Preset Pool

각 방 종류 별 Slot을 두고 게임 시작할 때 집 하나의 기본 구성에 맞춰 슬롯 안에서 방을 고르고자 함.

ex) 침실 A, 침실 B, 침실 C, 침실 D, 침실 E ⇒ Bedroom Pool

Bedroom Slot → 침실 A, 침실 B를 고르고자 함.

### 3.3 주의 해야 할 점: 중복 허용 금지

```
침실 1 → 침실 A
침실 2 → 침실 A
침실 3 → 침실 A
```

⇒ 같은 집에서는 방 프리셋 중복 금지.

> [구현 메모] 동일 카테고리의 **House 전체 슬롯 수 이상**의 서로 다른 프리셋이 있어야 중복 없이
> 배정할 수 있다. Floor_02 침실 4칸만 보면 최소 4종이며, 5종은 필수값이 아니다.
> 현재 `RoomSlotAssigner`도 풀이 슬롯보다 **적을 때만** 배정을 거부한다.
> 다락 등 전체 카테고리 배정과 최종 제작 수량은 MG-13 대기다(현재 Bedroom 3종).

### 3.4 계단 규칙

각 Floor는 계단을 통해 상하층과 연결한다.

추격 시 하나의 계단이 귀신에게 막히더라도 다른 경로를 사용할 수 있도록 주요 층에는
**계단 A와 계단 B의 두 개 이동 경로**를 배치한다.

> [구현 메모] v0.4 수치표는 **계단 층당 2개**를 고정값으로 둔다. 기존 A안 도면의 폭은 2.2m이며,
> B/C 도면의 폭·최종 경사·형태·계단참·단높이는 MG-7 대기다. 가구 운반 통과 여부는 §10.2 B에서 검증한다.

### 3.5 추격 동선 유지 규칙

Room Preset 랜덤 배치 후에도 House의 플레이어가 이동할 수 있는 **주요 이동 동선은 변경되지 않도록** 한다.

**중앙 홀, 복도, 계단 등 추격에 직접 영향을 주는 공간은 랜덤 생성하지 않고 고정**하고자 한다.

> 검증된 방 프리셋과 **같은 방식** — 집 밖 보관 자리에 두고 **뽑힌 것만 서버가 후보 지점으로
> 옮긴다**(`RoomPreset.ApplyTo` 패턴). 클라이언트는 `NetworkTransform` 복제로 같은 결과를 보고,
> 늦게 들어와도 어긋나지 않는다.

### 6.3 이전 Work Room 기준과 구현 확인 사항 [구현 메모]

- v0.3의 **Work Room 6~8개 / 청소 대상 20~25개**는 v0.4에 기재되어 있지 않다.
  최신 작업량과 생성 순서는 위 Type·Count 기준으로 읽는다. Work Room 제한을 별도로 유지할지는
  **MG-6 대기**이며, 문서에서 생략됐다는 이유로 시스템 삭제가 확정된 것으로 보지는 않는다.
- **귀신 관련 Content 1~3개**는 임시값이다. 귀신 콘텐츠의 상세 조건은
  [귀신 시스템 기획서](../project/ghost-system.md)를 따른다.
- 가구 Type 수·Type별 Count·총 작업량의 맵별 값과 랜덤 범위·분포는 미정이다(MG-21).
  위 **총 16개는 예시**이며 모든 맵의 고정 목표가 아니다.
- Type별 기존 가구를 어떻게 작업 대상으로 표시하고 수량에 포함할지, 반출 완료·진행도를 어떻게
  판정할지는 MG-22 및 청소·이사 작업 시스템(D-14)에서 정해야 한다.
- v0.4의 수량 부족 시 **해당 Furniture 추가 생성** 요구(§8)와 현재의
  **씬 사전 배치 + 서버 이동** 방식은 아직 연결되지 않았다. 미리 둔 가구를 보충 배치할지,
  런타임 스폰이 필요한지는 MG-23에서 확인한다. 이 문서 반영으로 ADR-0009를 변경하지 않는다.

**기존 House_01의 Spawn Point 자리는 소품 큐브로 미리 채워 두었다** — 해당 프리셋에는 아직 새 랜덤 선택 배선을 하지 않았으므로, 프리셋마다
바닥 Spawn Point 자리(상자 · 쓰레기통 · 빨래바구니)와 책상/협탁 위 Spawn Point 자리(컵 · 책 ·
화장품 상자)에 소품을 **고정으로** 놓았다. 10장 표대로 실제 메시 대신 큐브 하나로 때운 것이고,
전부 던질 수 있는 물리 가구다. 나중에 Spawn Point 시스템이 들어오면 이 좌표가 그대로
후보 지점이 된다. 위에 얹는 소품은 상판 윗면을 지지면 높이로 넘겨 정확히 앉힌다
(`MakePhysical(..., supportHeight)`) — 몇 cm 떠 있으면 세션 시작과 동시에 떨어진다.

**가구 원본** — 프리셋에 놓인 가구는 전부 `Assets/Prefabs/Furniture/` 프리팹의 인스턴스다
(MIG-6, 2026-08-31 커밋 `015f874` 로 가구 33종·문 3종을 실제로 구웠다 — `Game.unity` 에
`PrefabInstance` 108건). 같은 종류는 어느 방에 있든 같은 프리팹에서 나오므로, 치수를 고치려면
프리팹만 고치면 된다. 벽 방향이 다른 자리는 치수가 아니라 회전으로 맞춘다.

**배치 방식** — 프리셋을 프리팹으로 스폰하지 않는다. 맵 가구는 전부 씬에 놓인 `NetworkObject`라
호스트가 시작될 때 한꺼번에 스폰되는데, 프리셋을 프리팹으로 만들면 가구가 중첩 NetworkObject가
되고 스폰 경로가 둘로 갈린다. 대신 **이미 스폰된 가구를 서버가 슬롯으로 옮긴다**
(`RoomPreset.ApplyTo`). 클라이언트는 `NetworkTransform` 복제로 같은 결과를 보고, 늦게 들어와도
스폰 시점의 위치를 그대로 받으므로 "어떤 프리셋이 뽑혔는지"를 따로 동기화할 필요가 없다.

**중복 없음** — 풀을 Fisher-Yates로 섞어 앞에서부터 슬롯에 하나씩 준다. A·A 같은 조합은 나오지
않는다. 슬롯 수보다 프리셋이 적으면 배정 자체가 불가능하므로 생성 검증이 막는다.
세션을 다시 시작하면 먼저 모든 프리셋을 전시 자리로 되돌린 뒤 다시 뽑는다.

**문 동선 제약** — 침실1의 문은 방 서쪽 끝에서 4.3m(동쪽 칸막이 쪽), 침실2의 문은 0.72m
지점에 있다(도면의 L자 외곽과 욕실 위치 때문에 두 슬롯의 문 위치를 맞출 수 없다). 어느 슬롯에
뽑혀도 문이 가구를 쓸고 지나가지 않도록, 프리셋은 **방 남쪽 1.11m 띠를 비운다**(문짝 1.2m가
그리는 사분원). 예외는 두 문 사이 가운데 띠(방 중심 기준 x −0.93 ~ +1.45)로, 어느 문도
지나가지 않아 남쪽 벽까지 쓸 수 있다 — Bedroom_C의 상자가 여기 있다. 전시장 바닥에 이 금지
구역을 어두운 띠로 깔아 뒀다(`DoorSweep_KeepOut`).

**도면과 달라진 점** — 슬롯은 5.7 × 5.4m이며 세 프리셋 모두 도면의 핵심 가구 구성을
그대로 담는다(B의 서랍장·발치 협탁 포함). ×2 방의 빈 공간을 채우려고 넣었던 추가 가구 2개씩은
×1.5 축소 시 서로 겹쳐 제거했다. 방의 성격(A 1인용 침실 / B 부부 침실 / C 아이 방)은 유지하고,
남은 여백은 위의 고정 배치 소품이 메운다. 바닥 소품은 두 침실 모두의 문짝을 피하는 남쪽 가운데
안전 띠에 모아 둔다.

> [구현 메모] 위 단층 배율·소품 구성은 현재 구현의 기록이다. A안은 `MapScale` 1.0 결정이며,
> B/C 비교 프로토타입의 여백 정리는 §2에 별도로 기록했다. 맵 크기에 비례해 작업 가구를 늘리지 않고
> v0.4의 Type·Count와 §10.2 작업량 검증으로 조정한다.

프리셋 가구를 늘릴 때 지켜야 할 것:

- 남쪽 1.11m 띠는 그대로 비운다(두 문 사이 가운데 띠 x −0.93 ~ +1.45 제외).
- 북쪽 벽 가운데 창(폭 1.45m, 방 중심 기준 x ±0.725)은 키 큰 가구로 막지 않는다.
- 검증이 프리셋 × 슬롯 전 조합을 실제로 놓아 보므로, 겹치면 생성 단계에서 걸린다.

**생성 검증** — `HousePrototypeBuilder.ValidateRoomPresets`가 프리셋 × 슬롯 **전 조합**을 실제로
배치해 보고 (1) 벽·가구 겹침 (2) 문짝이 닫힘~열림 사이 어느 각도에서도 가구를 쓸지 않는지를
검사한다. 뽑기는 런타임이라 "가끔 나오는 조합만 깨지는" 버그를 여기서 잡지 않으면 알아채기 어렵다.

**최초 생성기 기록(2026-09-05):** 도면의 역할·방 치수를 유지하며 겹침을 피하도록 B안 주방 중심을
z=4.0, 세탁실 중심을 z=9.5로 조정했다. **2026-09-06에는 §2의 여백 정리 재설계로 대체됐다.**
현재 비교 프로토타입의 방 치수·좌표는 §2의 적용 표를 따르며 최종 도면 채택을 뜻하지 않는다.

창문 폭·높이, 앞마당·연결 바닥 폭, 실내 임시 조명, 난간 높이·두께와 전면 대문 폭은
`PlanVariantPrototypeSettings_Default`에 노출된 **[TEMP]** 값이다. 최종 도면/계단 규격이
정해지면 이 설정 에셋을 통해서만 조정하고, 현재 B/C 비교 프로토타입이 해당 값을 정식 확정으로
승격시키지는 않는다.

**현재 상태 (2026-09-06 갱신):** Unity MCP로 메뉴를 실행해 `Game.unity`에 저장까지 완료했다.
방 좌표는 원본 도면 값이 아니라 §2 "B·C안 적용된 실내 좌표"의 여백 정리 재설계 값이다 — 최초
실행 시 `ValidateRoomBounds`가 외곽 벽 이탈을 잡아냈는데, 원인은 이 문서 §2에 적어 둔 대로
**Unity 쪽 검증이 벽 두께 절반이 아니라 전체를 외곽선에서 뺀다**는 점을 처음에 놓쳤기 때문이다
(파이썬 사전 검증에서는 절반만 뺐었다). 좌표를 다시 계산하고 float 반올림 여유 0.02m를 더해
재실행하니 통과했다. `GhostHunter > 맵 B·C 프로토타입 검증`도 별도로 실행해 "가구 79개 / 79개,
계단 각 4개, 방 각 21개(7/8/6)"를 확인했다. Player의 CharacterController와 전역 밸런스 설정은
바꾸지 않았다. **수동 Play 이동·체감 확인은 하지 않았다** — 구조적 검증(겹침·경계·계단 클리어런스·
문 앞 가구)만 마쳤다.

#### 10.1.3 B안 가구 랜덤 배치 1차 구현 [구현 메모, 2026-09-12]

사용자가 **B안으로 가구 랜덤 스폰 제작 진행**을 선택했다. B안의 외곽과 2026-09-06에 저장한 실내를
제작 기준으로 삼는다. 가구는 [ADR-0009](decisions/ADR-0009-scene-placed-level-objects.md)의
**씬 프리팹 인스턴스 사전 배치 + 서버 이동**을 유지한다. 런타임 `Instantiate`/`Spawn`으로 가구를 만들지 않는다.

| 구성 | 역할 |
|---|---|
| `FurnitureSpawnSettings` | Pool ID·Spawn Type·Type 선택 수·풀별 최소/최대 수량·House/방 단위·작업 대상 여부·방 상한·시드·탐색 예산. 최초 설정은 Sofa 2 / Drawer 3 / Chair 5 / Box 6 = **16개 [TEMP]**, Type 4종 고정이며 인스펙터에서 범위 조정 가능 |
| `FurnitureSpawnPoint` | 지지면 위치·수평 회전·방 ID·Spawn Type·최대 치수·허용 Pool ID. 빈 허용 목록은 해당 Spawn Type 전체 허용 |
| `FurniturePlacementPlanner` | 시드 기반 후보 선택과 제한된 되돌아가기 탐색. 가구/지점 중복, 공간 겹침, Type별 수량, 방 제한을 함께 충족하는 **전체 계획**만 반환. 작업 대상이 적은 방을 우선하며 방별 강제 상한은 기본 0(미적용, MG-10 대기) |
| `FurnitureSpawnController` | 서버에서 씬 스폰·기존 프리셋 이동을 기다린 뒤 설정 검증 → Type/Count 추첨 → 물리 충돌 후보 제외 → 전체 계획 계산 → 가구 이동 → R 복구 자세 기록. 시드·완료 상태를 서버 쓰기 NetworkVariable로 복제 |
| `RandomFurnitureItem` | 보관 가구의 표시·충돌·물리·탐지 마커 제어. 서버만 이동·상태 변경, 위치는 `NetworkTransform`, 배치/대상 여부는 NetworkVariable로 전달. 미선택 가구는 숨기고 잡기도 서버에서 거부. 네트워크 해제 시 보관 자세로 복구 |
| `PlanBFurnitureSpawnSetup` | B안에 별도 풀·후보·Controller·Resetter를 추가하는 Editor 메뉴. 기존 프리팹을 사용하고 가구별 방 좌표를 코드에 넣지 않는다. 플레이어 4명 시작 위치를 기존 간격 그대로 B안 앞마당으로 이동 |

**초기 배치 범위와 한계**

- 기존 B안 인테리어 79개는 그대로 두고 **추가 풀 16개만 작업 대상으로 표시**한다. 기존 가구까지 집계할지는 MG-22 대기다.
- `RoomDimensions`를 읽어 홀·복도·계단 밖인 방 안에 Floor 후보를 최대 7개씩 만든다. 간격 1.5m,
  벽 여유 1.5m, 중앙 십자 통로 폭 1.2m는 설치용 **[TEMP] 설정**이다. 최대 가구 footprint로 안전 공간을
  보수적으로 확인하므로 작은 방·기존 가구가 많은 방은 후보가 7개 미만이거나 0개일 수 있고 경고한다.
- 현재 잠금 없는 B안 3개 층의 유효 후보를 사용한다. 잠긴 다락·스페셜 공간의 실제 대상 허용은
  MG-6·MG-15 대기이며, 이번 배치가 최종 잠금 규칙을 바꾸지 않는다.
- 일반 비대상 풀·방별 수량·4가지 Spawn Type을 데이터로 지원하지만, Desk/Sofa/Wall 소품 후보와
  Room Preset 교체 배선은 이번 설치 범위에 없다. B안 방 프리셋·귀신/은신처/세이프 존 이전도 후속 작업이다.
- 정적 Collider와 배치 가구끼리의 경계를 검사하며, 통로 영역에 후보를 만들지 않는다.
  **가구를 회전·운반해 최종 반출 지점까지 도달할 수 있는지는 검사하지 않는다**(MG-11).
- 풀 부족·유효 후보 부족·탐색 예산 초과는 부분 배치 없이 오류로 반환한다. 배치 도중 예외는 보관 상태로
  복구하고 `IsReady`를 올리지 않는다. 탐색 예산 20,000은 기술적 무한 탐색 방지값이며 정식 재추첨 정책(MG-12)은 미정이다.

**설치·검증 절차**

1. Unity에서 Play를 종료하고 `Assets/Scenes/Game.unity`를 열어 활성 씬으로 선택한다. 스크립트 임포트와 컴파일을 기다린다.
2. `GhostHunter > 맵 B안 가구 랜덤 배치 설치`를 실행한다. 메뉴는 설정 에셋
   `Assets/Settings/Gameplay/FurnitureSpawnSettings_PlanB.asset`과 씬 배선을 만들고, seed 0~15 전체 배치·시작 위치 검사 후
   **Game 씬을 저장**한다. 이어 NGO 식별자 갱신·중복 검사를 수행한다. 기존 시스템이 있으면 가구·후보를 중복 생성하지 않고 검증·식별자 갱신·저장한다.
   방별 후보 수는 필수 수량이 아니라 최대치다. 안전 후보가 없는 방은 제외되며, 집 전체 후보가 설정된 가구 16개를 배치할 수 있는지는 설치 검증이 별도로 확인한다.
3. `GhostHunter > 맵 B안 가구 랜덤 배치 검증`으로 수량·충돌·시작 위치·NGO 식별자를 재검사한다.
   후보 부족 시 `SpawnPoints`에 유효 후보를 추가하거나 위치를 조정한 후 다시 검사한다. 이 메뉴 자체는 저장하지 않는다.
4. Bootstrap부터 Local Host를 시작한다. B안 앞마당 시작, 완료 로그의 16개 배치, Q 탐지 대상, 잡기·던지기,
   R 복구와 세션 재시작을 확인한다. 고정 시드 재현과 다른 시드 분포를 비교한다.
5. Host/Client에서 배치·대상 상태 일치, 늦은 참가, 클라이언트의 보관 가구 잡기 거부를 확인한다.
   최종 Steam 검증은 2대 PC·2개 계정에서 수행한다.

**이번 검증:** Gameplay·Editor·EditMode 어셈블리의 C# 빌드 **경고 0·오류 0**.
`FurniturePlacementPlannerTests` **13/13 통과**(Unity 의존성이 없는 계획 코드와 NUnit 테스트를 standalone .NET에서 실행).
100개 시드의 16개 수량·중복 방지, 같은 시드 재현, 방/풀 제한, 층 분리, 충돌, 되돌아가기·탐색 상한·잘못된 입력을 검사했다.
열린 Unity 에디터의 자동 임포트로 신규 `.meta`가 생성됐으며, Editor 로그에서 Gameplay·Editor·테스트 어셈블리의
**컴파일·NGO IL 후처리·도메인 재로드 성공**도 확인했다. 이후 설치 메뉴가
`FurnitureSpawnSettings_PlanB.asset`, 풀 16개, 안전 후보 91개와 B안 앞마당 시작 위치를 Game 씬에 저장했고 내부 seed 0~15 검증을 통과했다.
MCP 로컬 서버·세션 연결도 확인했다. **Unity Test Runner·Host/Client Play 검증은 미실행**이다.

```text
→ 일반 Spawn Point 선택·일반 Object 생성

→ 최종 검증
→ 플레이 시작
```

### 11.2 상세 흐름

세부 생성 순서는 **§7**, 조건별 재선정·추가 생성·재배치는 **§8**을 따른다.
검증에서 조건을 위반하면 해당 단계의 처리 후 결과를 다시 확인한다.

> [구현 메모] v0.3의 Work Room 선정·Work Room 한정 콘텐츠 생성 단계는 최신 흐름에 넣지 않는다.
> 해당 방 제한의 존치 여부는 MG-6에서 확인한다.
