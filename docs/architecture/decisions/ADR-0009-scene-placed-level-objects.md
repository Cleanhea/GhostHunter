# ADR-0009: 가구·문·붙박이는 프리팹 인스턴스로 씬에 배치한다

- **상태**: Accepted
- **날짜**: 2026-08-19
- **결정자**: MinGiHong
- **관련**: [../map-generation.md](../map-generation.md), [../furniture-physics.md](../furniture-physics.md), [../../conventions/unity-assets.md](../../conventions/unity-assets.md)

## 배경 (Context)

Unity 에셋 규약의 일반론은 "씬에 직접 배치한 오브젝트를 그대로 두지 않는다. 재사용 대상은 프리팹화한다"이다.
이 문장이 **두 가지 서로 다른 것**을 뭉뚱그려서 혼란이 생긴다.

1. **프리팹 에셋으로 만드는가** — 재사용 단위를 정의하는 문제
2. **런타임에 스폰하는가, 씬에 미리 배치하는가** — 배치 시점의 문제

GhostHunter의 현재 상태는 **둘 다 아니다.** `HousePrototypeBuilder`가 `GameObject.CreatePrimitive`로
익명 씬 오브젝트를 만들고, 그것을 씬에 남긴다. 1번은 안 되어 있고 2번은 되어 있다.

## 검토한 선택지 (Options)

| 선택지 | 1. 프리팹 에셋 | 2. 배치 시점 | 평가 |
| --- | --- | --- | --- |
| A. 현재 상태 | ❌ 익명 씬 오브젝트 | 씬 배치 | 재사용·일괄 수정 불가 |
| B. **프리팹 에셋 + 씬 인스턴스** | ✅ | 씬 배치 | 채택 |
| C. 프리팹 에셋 + 런타임 서버 스폰 | ✅ | 스폰 | 아래 §근거 참조 |

## 결정 (Decision)

**B를 채택한다.** 가구·문·붙박이·방 프리셋은 **프리팹 에셋으로 만들되, 씬에 인스턴스로 배치한다.**

- 1번(프리팹화)은 **한다.** 재사용·배리언트·일괄 수정을 위해서다.
- 2번(런타임 스폰)은 **하지 않는다.** 아래 근거.

예외적으로 스폰하는 것: 플레이어(NGO Player Prefab), 그리고 앞으로 생길 런타임 생성물(투사체·이펙트).

## 근거 (Rationale)

### 프리팹화(1번)를 하는 이유

- 가구 25종의 콜라이더·`Rigidbody`·`NetworkObject`·머티리얼 설정을 **한 곳에서 고칠 수 있다.**
  지금은 같은 종류 가구를 고치려면 씬에서 인스턴스를 하나씩 찾아야 한다.
- 무게 등급(light/heavy) 같은 변형을 프리팹 배리언트로 표현할 수 있다.
- `FurnitureDefinition` SO가 "기본 프리팹 참조"를 갖는 설계인데, 참조할 프리팹이 없다.

### 런타임 스폰(2번)으로 바꾸면 잃는 것

이것이 "퇴보"라고 부른 부분이다. 다섯 가지다.

**1. 레벨 디자인이 씬 파일을 떠난다.**
가구 위치가 씬에 있으면 에디터에서 보면서 옮긴다. 스폰이면 좌표가 코드나 데이터로 이동한다.
프로젝트 규약이 이미 이걸 경고하고 있다 — *"생성 도구에 방별 가구 좌표를 다시 심지 않는다(손으로 한 배치와 겹친다)"*.
스폰 방식은 그 함정으로 직행하는 길이다.

**2. 접속 시 스폰 폭풍.**
씬 배치 `NetworkObject`는 씬 동기화로 양쪽이 **같은 오브젝트를 찾아 붙는다**(`GlobalObjectIdHash` 기준).
스폰이면 서버가 30개 오브젝트의 스폰 메시지를 보내고 각 클라이언트가 인스턴스화한다.
접속 순간 트래픽과 히칭이 늘고, 늦게 접속한 클라이언트일수록 불리하다.

**3. 방 프리셋이 중첩 `NetworkObject` 문제에 빠진다.**
현재 `RoomSlotAssigner`는 **이미 스폰된 가구를 옮긴다.** 프리팹을 스폰하는 방식이면
프리셋 루트 아래에 자식 `NetworkObject`가 들어가고, NGO는 중첩 `NetworkObject`를 제대로 다루지 못한다.
"이동" 방식은 이 문제를 **설계로 회피한 것**이지 우연이 아니다.

**4. 정적 배칭·라이트맵·오클루전 대상에서 빠진다.**
씬에 있는 오브젝트만 베이크된다. 붙박이(`Fixtures/`)를 정적 콜라이더로 두는 것도 같은 이유다.
런타임 스폰은 전부 동적 오브젝트가 된다.

**5. 초기 상태의 결정성이 사라진다.**
씬에 있으면 모든 피어가 같은 초기 배치에서 출발한다. 스폰은 순서·타이밍에 의존하고,
`FurnitureResetter`(R키로 초기 위치 복구)가 참조할 "초기 위치"의 출처가 모호해진다.

### 정리

**"프리팹화한다"와 "스폰한다"는 별개다.** 일반론의 전반부(프리팹 에셋으로 만든다)는 이득만 있으므로 채택하고,
후반부(씬에 배치하지 않는다)는 레벨 오브젝트에 한해 예외로 둔다.
이 둘을 한 문장으로 묶어 놓은 규약이 혼란의 원인이었다.

## 결과 (Consequences)

### 긍정
- 가구 종류별 설정을 프리팹에서 한 번에 고친다.
- 씬 동기화·라이트맵·결정성 이득을 그대로 유지한다.
- `FurnitureDefinition`의 프리팹 참조 필드가 의미를 갖는다.

### 부정 / 감수하는 비용
- **프리팹화 자체가 마이그레이션 작업이다.** `HousePrototypeBuilder`가 프리미티브 생성 대신
  프리팹 인스턴스화(`PrefabUtility.InstantiatePrefab`)를 하도록 고쳐야 하고,
  기존 씬 오브젝트를 프리팹 인스턴스로 교체해야 한다.
- 프리팹 인스턴스 오버라이드가 늘면 "프리팹을 고쳤는데 씬에 반영이 안 된다"가 생긴다.
  → 오버라이드는 **위치·회전에 한정**한다. 그 외 값을 씬에서 바꾸지 않는다.
- 프리팹 GUID가 새로 생기므로 씬 참조가 재작성된다. 다른 마이그레이션과 같은 커밋에 섞지 않는다.

## 재검토 조건

- 맵이 런타임 절차 생성으로 바뀌어 "씬에 미리 배치"가 성립하지 않게 될 때
  (현재 [../map-generation.md](../map-generation.md)의 방 프리셋 시스템은 **미리 배치 + 이동**이므로 해당 없음.
  **2026-09-05 결정**으로 v0.3 Spawn Point 소형 오브젝트도 같은 방식을 쓴다 — 런타임 스폰하지 않는다)
- 가구 수가 씬 로드 시간·메모리에 부담이 될 만큼 늘어날 때
