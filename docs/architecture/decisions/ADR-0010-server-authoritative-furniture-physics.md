# ADR-0010: 가구 물리는 서버 권위로 시뮬레이션한다

- **상태**: Accepted
- **날짜**: 2026-08-19
- **결정자**: MinGiHong
- **관련**: [ADR-0001](ADR-0001-steam-p2p-facepunch-transport.md), [ADR-0008](ADR-0008-owner-authoritative-player-movement.md), [../networking.md](../networking.md), [../throw-system.md](../throw-system.md)

## 배경 (Context)

이 게임의 핵심은 **여러 명이 같은 물리 오브젝트를 동시에 조작하는 것**이다.
가구 하나에 홀더가 최대 2명 붙고, 두 사람의 조준 방향 평균으로 부양 목표점이 정해지며,
날아간 가구가 다른 가구를 쳐서 연쇄가 일어난다.

물리 권위를 어디에 둘지 정해야 한다. 잘못 정하면 **두 클라이언트가 서로 다른 세계를 보게 된다.**

토폴로지는 Steam P2P 리슨 서버로 고정되어 있다([ADR-0001](ADR-0001-steam-p2p-facepunch-transport.md)).
즉 "서버"는 호스트 플레이어의 프로세스다.

## 검토한 선택지 (Options)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. **서버 권위** — 서버만 `Rigidbody` 시뮬레이션, 클라는 kinematic + `NetworkTransform` 보간 | 세계가 하나다. 2인 흡착 판정이 한 곳. 연쇄 충돌이 자동으로 일관됨 | 클라이언트 입력에 RTT만큼 지연이 실린다 |
| B. 소유자 권위 — 잡은 사람이 물리를 돌리고 결과를 복제 | 잡은 사람은 지연 0 | **2인 흡착에서 소유자가 둘이 된다.** 연쇄 충돌 시 소유권이 오브젝트마다 갈려 서로 다른 결과가 나옴 |
| C. 클라이언트 예측 + 서버 재조정(롤백) | 지연 은폐 + 권위 유지 | 물리 롤백은 결정적 시뮬레이션을 요구한다. PhysX는 결정적이지 않다. 구현 규모가 게임 본체급 |
| D. 분산 물리 — 오브젝트별 권위 분배 | 부하 분산 | 권위 경계를 넘는 충돌에서 상태가 갈린다. A의 일관성 이득을 잃고 B의 문제를 그대로 받음 |

## 결정 (Decision)

**A를 채택한다.**

- 가구 `Rigidbody`는 서버에서만 non-kinematic. 클라이언트에서는 `isKinematic = true`.
- 클라이언트는 **의도만** RPC로 보낸다: 대상 `NetworkObjectReference`, 조준 방향 `Vector3`.
- 서버 전용 컴포넌트(`FurnitureHoverMotor`, `FurnitureLauncher`)는 `OnNetworkSpawn`에서 스스로 꺼진다.
- **클라이언트에서 `Rigidbody`에 직접 힘을 가하지 않는다.** 이 규칙은 예외 없다.

## 근거 (Rationale)

**1. B는 이 게임의 핵심 메커닉과 양립하지 않는다.** 2인 흡착은 "두 사람이 같은 오브젝트를 동시에
조작한다"이고, 소유자 권위는 "한 오브젝트에 조작자는 하나"를 전제한다. 소유권을 왔다 갔다 넘기면
그 전환 순간마다 물리 상태가 튄다.

**2. 연쇄 충돌이 B·D를 배제한다.** 던진 가구가 다른 가구를 치는 것이 명시적 요구사항이다.
권위가 오브젝트마다 다르면 충돌 지점에서 양쪽이 서로 다른 반발을 계산하고, 그 차이가 누적된다.

**3. C는 이 규모에서 불가능하다.** PhysX는 결정적이지 않아 롤백 재시뮬레이션이 같은 결과를 보장하지 않는다.
결정적 물리를 쓰려면 물리 엔진 자체를 바꿔야 한다.

**4. 지연 비용은 연출로 상당 부분 가려진다.** 크로스헤어, 윤곽선, 차지 게이지는 클라이언트에서
즉시 반응한다. 플레이어가 "눌렀는데 반응이 없다"고 느끼는 구간이 그만큼 짧아진다.

## 결과 (Consequences)

### 긍정
- 모든 피어가 같은 물리 세계를 본다. "내 화면에서는 맞았는데"가 발생하지 않는다.
- 2인 흡착·연쇄 충돌·발사각 보정이 전부 한 프로세스 안에서 계산된다.
- 클라이언트 치팅으로 가구를 날릴 수 없다(호스트 제외).

### 부정 / 감수하는 비용

**이것이 이 결정의 실질적 리스크다. 튜닝 전에 반드시 읽는다.**

1. **입력 → 반응 사이에 RTT가 실린다.** 홀드를 눌러 가구가 실제로 뜨기 시작할 때까지 왕복 지연이 걸린다.
   Steam SDR 릴레이는 직결이 안 되면 경유하므로 **LAN보다 지연이 크고 변동이 있다.**
   → **LAN·로컬 기준으로 던지기 수치를 튜닝하면 안 된다.** 실제 원격 접속에서 반드시 재확인한다.
   `hoverDistance`·`springStiffness`·`chargeTime`은 지연 체감에 직접 영향을 준다.
2. **호스트만 유리하다.** 호스트는 지연 0, 게스트는 RTT. 손맛 판정을 호스트 화면으로만 하면 안 된다.
   플레이테스트는 MUST 게스트 쪽에서도 한다.
3. **호스트가 물리와 렌더를 동시에 진다.** 가구가 여러 개 동시에 깨어나면 호스트만 프레임이 떨어진다.
   현재 규모(가구 25 + 문 5)에서는 여유가 있으나, 콘텐츠가 늘면 재측정한다.
4. **`NetworkTransform` 대역폭.** 잠든 `Rigidbody`는 전송하지 않지만 연쇄 충돌로 여러 개가 동시에
   깨어나면 트래픽이 몰린다. 호스트의 **업로드** 회선이 상한이다.

### 완화책 (구현 방침)
- 연출(윤곽선·크로스헤어·게이지)은 클라이언트에서 즉시 반응시킨다. **상태만 서버를 기다린다.**
- 발사 방향은 클라이언트가 보낸 조준 벡터를 쓴다 → 조준에는 지연이 없다.
- `NetworkTransform` 보간을 켜고 불필요한 축 동기화를 끈다.
- 튜닝 수치는 SO에 두고 원격 접속 상태에서 조정한다.

## 재검토 조건

- 원격 플레이테스트에서 지연 때문에 **던지기 손맛이 성립하지 않는다는 판정**이 날 때
  → 그때 검토할 것은 C(예측)가 아니라 **메커닉 조정**(홀드 진입을 로컬 연출로 더 가리기)이 먼저다
- 호스트 프레임이 콘텐츠 증가로 무너질 때
- 동시 활성 가구 수가 대역폭 상한에 닿을 때
