# ADR-0011: 로컬(UnityTransport) 개발 경로를 어떻게 둘 것인가

- **상태**: **Accepted**
- **날짜**: 2026-08-20
- **결정자**: MinGiHong
- **관련**: [ADR-0001](ADR-0001-steam-p2p-facepunch-transport.md), [../networking.md](../networking.md), [../steam.md](../steam.md), [../../workflow/testing.md](../../workflow/testing.md)

## 배경 (Context)

이 프로젝트는 트랜스포트를 두 개 두고 런타임에 전환한다.

| 모드 | 트랜스포트 | 용도 |
| --- | --- | --- |
| `TransportMode.Steam` | FacepunchTransport | 실제 플레이 경로 |
| `TransportMode.Local` | UnityTransport (127.0.0.1:7777) | 혼자 로직 검증, LAN 크로스머신 확인 |

전환 수단이 셋이다: 개발용 HUD(F1)의 `모드:` 버튼, `ConnectionManager` 인스펙터,
커맨드라인 `-transport=local` / `-transport=steam`.

**이 구성이 존재하는 이유는 Steam 테스트 마찰이다.**
같은 Steam 계정으로 두 인스턴스를 P2P 연결할 수 없다. SteamId가 같아서 자기 자신에게 연결하는 꼴이 된다.
Unity의 Multiplayer Play Mode도 Steam 계정을 공유하므로 마찬가지다.
**실제 2인 검증에는 PC 2대 + Steam 계정 2개가 필요하다.**
그래서 일상 개발은 UTP로, Steam 경로는 주기적으로 검증하는 흐름이 자리잡았다.

한편 네트워크 규약의 일반론은 반대를 말한다:
*"`UnityTransport`를 런타임 경로에 남기지 않는다. 자동화 테스트 용도로만 예외 허용."*
*"IP/포트 직접 입력 접속 UI를 만들지 않는다. 연결 진입점은 Steam Lobby뿐이다."*

두 요구가 충돌한다. 어느 쪽으로 갈지 정해야 한다.

## 검토한 선택지 (Options)

### A. 현재 유지 — 런타임 이중 트랜스포트

`ConnectionManager`가 두 트랜스포트를 들고 런타임에 전환한다. 개발용 HUD로 고른다.

| | |
| --- | --- |
| **이점** | **혼자서 2인 로직을 검증할 수 있다.** 빌드 실행 → Host, 에디터 플레이 → Join. 이게 매일 쓰는 루프다 |
| | Steam 없이도 개발이 진행된다. Steam 클라이언트 미실행·계정 문제에 개발이 막히지 않는다 |
| | LAN 크로스머신(Windows ↔ Mac)으로 **Steam 변수를 뺀 채** 네트워크 로직만 확인할 수 있다 |
| | 문제 발생 시 원인이 Steam 쪽인지 게임 로직 쪽인지 **바로 갈린다** |
| | 이미 구현·검증되어 있다. 추가 비용 0 |
| **비용** | 제품 빌드에 쓰이지 않는 코드 경로가 런타임에 남는다 |
| | `ConnectionManager`가 트랜스포트 전환 로직을 들고 있어 복잡도가 있다 |
| | 두 경로의 동작이 갈릴 수 있다. Local에서 되는데 Steam에서 안 되는 버그가 늦게 발견된다 |
| | 실수로 Local 모드로 빌드가 나가면 아무도 접속하지 못한다 |

### B. 규약대로 제거 — Steam 단일 경로 + 테스트 어셈블리

런타임에서 UTP를 걷어내고, `UnityTransport`는 PlayMode 테스트 어셈블리에서만 코드로 구성한다.

| | |
| --- | --- |
| **이점** | 런타임 경로가 하나다. 제품에서 도는 코드와 개발에서 도는 코드가 같다 |
| | `ConnectionManager`에서 전환 분기가 사라진다 |
| | "Local에서만 되는 버그"가 원천적으로 없다 |
| **비용** | **일상 1인 검증 루프가 사라진다.** 대체재가 PlayMode 테스트인데 **현재 테스트 어셈블리가 0개다** |
| | PlayMode 테스트로 커버되는 것은 로직이지 **체감**이 아니다. 던지기 손맛은 사람이 두 화면을 봐야 한다 |
| | 손으로 뭔가 확인하려면 매번 PC 2대 + 계정 2개를 세팅해야 한다 |
| | 전환 비용: 테스트 어셈블리 구축 + 네트워크 테스트 작성이 선행되어야 한다 |

### C. 절충 — 개발 빌드 전용으로 격리

UTP 경로를 유지하되 `DEVELOPMENT_BUILD || UNITY_EDITOR`로 감싸고, 스크립팅 심볼(`GH_LOCAL_TRANSPORT`)로 통제한다.

| | |
| --- | --- |
| **이점** | 일상 검증 루프가 그대로 유지된다 |
| | **릴리스 빌드가 Local 모드로 나갈 수 없다.** A와의 실질적 차이는 이것 하나뿐이다 |
| | 규약의 의도("제품 연결 진입점은 Steam Lobby뿐")를 컴파일러 수준에서 표현한다 |
| **비용** | 조건부 컴파일이 `ConnectionManager` 전반에 흩어진다 |
| | 릴리스 빌드에서만 나는 컴파일 에러를 놓칠 수 있다 → CI에서 릴리스 구성 컴파일을 돌려야 안전하다 |
| | 여전히 두 경로의 동작이 갈릴 여지는 남는다 |

> **정정 (2026-08-20).** 이 절의 초판은 "UTP 참조가 릴리스 빌드에서 빠져 빌드 크기·의존이 줄어든다"를
> C의 이점으로 적었다. **틀렸다.** `com.unity.transport`는 NGO의 의존 패키지라(`packages-lock.json`에서
> `depth: 1`, NGO가 2.6.0 이상을 요구) 우리가 무엇을 하든 프로젝트에 들어온다.
> 게다가 `ConnectionManager._localTransport`는 이미 구체 타입이 아니라 기반 타입 `NetworkTransport`로
> 받고 있어 **우리 코드에는 `UnityTransport` 타입 참조가 애초에 없다.**
> C가 실제로 사는 것은 빌드 크기가 아니라 **"잘못된 모드로 출시될 수 없다"** 하나다.

### D. A + 빌드 시 가드 (조건부 컴파일 없이)

UTP 경로를 그대로 두되, 빌드 전처리(`IPreprocessBuildWithReport`)에서
`NetworkRig` 프리팹의 `_transportMode`가 `Steam`인지 검사하고 아니면 **빌드를 실패시킨다.**

| | |
| --- | --- |
| **이점** | C가 막으려는 사고(릴리스가 Local로 나감)를 **같은 수준으로 막는다** |
| | 조건부 컴파일이 0곳이다. `ConnectionManager`가 읽기 쉬운 채로 남는다 |
| | 릴리스 구성에서만 나는 컴파일 에러 위험이 없다 |
| | 구현이 에디터 스크립트 한 개(20줄 남짓)로 끝난다 |
| **비용** | `-transport=local` 커맨드라인은 릴리스 빌드에서도 여전히 먹는다 |
| | 코드 자체는 제품 빌드에 남는다(규약의 문언에는 어긋난다) |

> 커맨드라인이 남는 것은 실질적 위험이 아니다. 플레이어가 자기 빌드를 Local로 띄우면
> 아무에게도 접속하지 못할 뿐이고, 이것으로 남의 세션에 영향을 줄 수 없다.

## 권고

**D를 권한다** (2026-08-20 갱신. 이전 권고는 C였다).

B는 방향은 옳지만 **선행 조건이 갖춰지지 않았다.** 테스트 어셈블리가 0개인 상태에서 UTP를 걷어내면
검증 수단이 "PC 2대"밖에 남지 않고, 그건 개발 속도를 크게 떨어뜨린다.

**A·C·D는 개발 경험이 완전히 같다.** 셋의 차이는 오직 "릴리스가 Local로 나가는 사고를 어떻게 막는가"이고,
D가 같은 보호를 조건부 컴파일 없이 얻는다. C의 `#if` 는 `ConnectionManager` 전반(전환 분기·커맨드라인
파싱·`StartLocalClient`)에 흩어지는데, 그 대가로 사는 것이 D와 같다면 치를 이유가 없다.

규약이 UTP를 금지하는 진짜 이유는 **"제품 UI에 IP 접속 경로가 노출되는 것"** 인데,
로컬 경로는 이미 개발용 HUD 뒤에만 있고 제품 메뉴(`Title`/`Lobby`)에는 없다.
남은 위험은 "실수로 Local 모드 빌드가 나간다" 하나뿐이고, 그것만 막으면 된다.

B로 가려면 **먼저 테스트 어셈블리와 네트워크 PlayMode 테스트를 만들고**, 그것이 실제로
일상 검증을 대체하는지 확인한 다음에 걷어내는 순서가 맞다. 그때 이 ADR을 다시 연다.

## 결정 (Decision)

**D를 채택한다.** 로컬(UTP) 경로를 런타임에 그대로 두고, 조건부 컴파일 대신
**빌드 전처리 가드**로 릴리스가 Local 모드로 나가는 것을 막는다.

구현: `Assets/Scripts/Editor/TransportModeBuildGuard.cs`

| 인터페이스 | 검사 대상 |
| --- | --- |
| `IPreprocessBuildWithReport` | 모든 프리팹의 `ConnectionManager` |
| `IProcessSceneWithReport` | 빌드에 포함되는 각 씬의 `ConnectionManager` |

- 개발 빌드(`BuildOptions.Development`)는 면제한다. Local 이 정상 용법이다.
- 릴리스 빌드에서 `Steam` 이 아니면 `BuildFailedException` 으로 **빌드를 중단**한다.
- 씬 경로를 함께 검사하므로, 리그가 프리팹에서 `Bootstrap` 씬으로 옮겨가도(MIG-3) 그대로 동작한다.

### 이 결정을 앞당긴 실물 증거

결정 시점에 확인해 보니 **`NetworkRig.prefab` 이 이미 `_transportMode: 1`(Local)로 커밋되어 있었다.**
씬 오버라이드도 없어 그대로 빌드에 실리는 상태였다.

당장 깨지지는 않았다. 메뉴 흐름이 양쪽에서 Steam 을 명시적으로 강제하기 때문이다
(`LobbyController.HandleStartClicked` 와 `ConnectionManager.ConnectToSteamHost` 진입부).
**그러나 이것은 방어 코드 두 개가 우연히 막아준 것이지 설계된 보호가 아니다.**
기본값에 의존하는 경로가 하나만 생겨도 조용히 Local 로 동작한다.

가정했던 사고가 이미 일어나 있었다는 점이 A(현상 유지)를 배제하는 근거가 되었다.
프리팹 값은 이 ADR과 함께 `Steam` 으로 되돌렸다.

## 어느 쪽으로 가든 지킬 것

- **게임 로직은 트랜스포트 구현을 직접 참조하지 않는다.** `FacepunchTransport`·`UnityTransport`·`SteamClient`
  타입이 `Gameplay`·`UI`에 등장하면 안 된다. 이 규칙이 깨지면 세 선택지가 전부 불가능해진다.
- 로컬 경로는 **개발용 HUD 뒤에** 둔다. 제품 메뉴(`Title`/`Lobby`)에 노출하지 않는다.
- 트랜스포트 전환은 **세션 정지 중에만** 허용한다.

## 결과 (Consequences)

### 긍정
- 일상 1인 검증 루프가 그대로 유지된다.
- 릴리스가 Local 로 나가는 사고가 빌드 단계에서 확실히 끊긴다.
- 조건부 컴파일이 0곳이라 `ConnectionManager` 가 읽기 쉬운 채로 남는다.
- 리그가 프리팹에서 씬으로 옮겨가도 가드를 고칠 필요가 없다.

### 부정 / 감수하는 비용
- 로컬 경로 코드가 릴리스 빌드에도 남는다. 규약의 문언에는 어긋난다.
- 릴리스 빌드에서도 `-transport=local` 커맨드라인이 먹는다.
  → 실질 위험이 아니다. 플레이어가 자기 빌드를 Local 로 띄우면 아무에게도 접속하지 못할 뿐이고,
  이것으로 남의 세션에 영향을 줄 수 없다.
- 두 경로의 동작이 갈릴 여지는 그대로 남는다. "Local 에서만 되는 버그"는 여전히 가능하다.

### 후속 작업
- [x] `TransportModeBuildGuard` 구현 (프리팹 + 씬 경로)
- [x] `NetworkRig.prefab` 의 `_transportMode` 를 Steam 으로 정정
- [x] 가드 동작 검증 — Steam 통과, Local 에서 `BuildFailedException`
- [ ] 실제 릴리스 빌드 1회로 종단 검증 (가드가 빌드 파이프라인에서 실제로 불리는지)
- [ ] MIG-3 에서 리그를 `Bootstrap` 씬으로 옮긴 뒤 씬 경로 검사가 도는지 확인

## 재검토 조건

- 테스트 어셈블리가 구축되고 네트워크 PlayMode 테스트가 일상 검증을 대체할 때 → B 재검토
- 전용 QA 환경(PC 2대 상시)이 생겨 Steam 경로 검증 마찰이 사라질 때 → B 재검토
- **"Local 에서만 되는 버그"가 실제로 두 번 이상 발생할 때 → 즉시 B로 전환**
