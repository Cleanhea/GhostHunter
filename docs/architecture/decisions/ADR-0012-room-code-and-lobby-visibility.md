## 1. 방 코드 형식 — 확정

**6자리 커스텀 코드를 쓴다.** (2026-08-19 결정)

```
문자셋: ABCDEFGHJKLMNPQRSTUVWXYZ23456789   (32자 — 0/O, 1/I 제외)
길이:   6                                  (약 10.7억 조합)
저장:   로비 데이터 gh_room_code
```

기각한 대안 — **`Lobby.Id` 64비트 숫자 원문**. 20자리 숫자를 사람이 불러주거나 받아 적을 수 없다.
6자리 코드는 음성으로 전달 가능하고, 혼동 글자를 뺐으므로 받아 적기도 안전하다.
`Lobby.Id`는 `gh_host_steam_id`와 함께 내부적으로만 쓴다.

## 2. 로비 데이터 스키마 — 확정

에이전트 판단으로 아래와 같이 정한다. 키를 추가·변경하면 MUST 이 표를 갱신한다.

| 키 | 스코프 | 값 | 목적 | 상태 |
| --- | --- | --- | --- | --- |
| `gh_game` | 로비 | `"GhostHunter"` | **App ID 480 공용 로비 목록에서 우리 방만 거르는 1차 필터** | **구현됨 (2026-08-21)** |
| `gh_room_code` | 로비 | 6자리 코드 | 방 코드 검색 필터 | 구현됨 |
| `gh_host_steam_id` | 로비 | `ulong` | P2P 접속 대상. 없으면 `lobby.Owner.Id`로 폴백 | 구현됨 |
| `gh_net_fingerprint` | 로비 | 지문 문자열 | 빌드 호환성 검사 | 구현됨 |
| `gh_game_started` | 로비 | `"1"` | 호스트가 세션을 띄웠다는 신호 | 구현됨 |
| `gh_joinable` | 로비 | `"1"` / `"0"` | 난입 허용 여부를 UI에 표시 | **신규 — §4 확정 후** |
| `gh_ready` | **멤버** | `"1"` | 게스트 준비 상태 | 구현됨 |

**`version` 키는 두지 않는다.** `gh_net_fingerprint`가 그 역할을 포함하며 더 많은 정보를 담는다
(NGO 직렬화에 영향을 주는 변경 전반). 같은 사실을 두 키로 나눠 들면 어긋난다.

**`gh_game` 추가가 필요한 이유** — App ID 480은 Valve 공개 테스트 앱이라 **다른 게임의 로비가 같은
목록에 섞인다.** 현재는 `gh_room_code` 키로만 검색하는데, 우리가 나중에 "방 목록" 화면을 만들거나
코드 없이 조회할 일이 생기면 필터가 없다. 지금 넣어두는 비용이 거의 0이다.

## 3. 로비 가시성 — **모순 있음, 결정 필요**

> **사용자 지시는 "FriendsOnly 확정"이었으나, 그것과 6자리 방 코드 참가는 Steam에서 양립하지 않는다.**

### 왜 양립하지 않는가

Steam의 `ELobbyType` 중 **로비 목록 검색(`RequestLobbyList`)에 잡히는 것은 `Public`뿐이다.**

| 로비 타입 | 목록 검색 | 친구 초대 | ID 직접 참가 |
| --- | --- | --- | --- |
| `Private` | ❌ | ✅ | ✅ |
| **`FriendsOnly`** | **❌** | ✅ | ✅ |
| `Public` | ✅ | ✅ | ✅ |
| `Invisible` | ❌ | ✅ | ✅ |

우리 방 코드 참가 구현(`JoinLobbyByCodeAsync`)은 `LobbyList.WithKeyValue(gh_room_code, code)` 검색에 의존한다.
**로비를 `FriendsOnly`로 만들면 이 검색이 아무것도 반환하지 않는다.** 방 코드 기능이 통째로 죽는다.

현재 코드에는 `SetFriendsOnly()`와 `SetPublic()` 분기가 둘 다 있다
([`SteamLobbyManager.cs`](../../../Assets/Scripts/Systems/Steam/SteamLobbyManager.cs)).
`_friendsOnly = true`로 두면 방 코드가 동작하지 않는 상태다.

### 선택지

| 선택지 | 방 코드 | 친구 초대 | 모르는 사람 난입 위험 |
| --- | --- | --- | --- |
| **A. `Public` + 코드 검색 + 접속 승인 재검증** | ✅ | ✅ | 낮음 (아래 근거) |
| B. `FriendsOnly` + 초대 전용 (방 코드 폐기) | ❌ | ✅ | 없음 |
| C. `Public` + 코드 검색만 (현재 상태) | ✅ | ✅ | 중간 — 로비 ID를 알면 코드 없이 들어옴 |

### 권고 — A

**로비는 `Public`으로 만들되, 실질적 접근 통제를 두 겹으로 건다.**

1. **탐색 차단** — 6자리 코드(약 10.7억 조합)를 모르면 검색으로 찾을 수 없다.
   우리 게임에 "방 목록" 화면을 **만들지 않는다.** 코드 입력만이 진입점이다.
2. **접속 차단** — NGO `ConnectionApproval` 콜백에서 **접속 페이로드의 방 코드를 서버가 재검증**한다.
   로비에는 들어와도 게임 세션에는 붙지 못한다.

2번이 핵심이다. `Public` 로비는 로비 ID만 알면 코드 없이 입장할 수 있으므로 로비 계층만으로는 부족하다.
접속 승인 계층에서 한 번 더 막으면 **`FriendsOnly`가 주려던 보호를 실질적으로 확보**하면서
방 코드 기능을 살릴 수 있다. 이미 `gh_net_fingerprint`로 빌드 호환성을 거르고 있으므로,
같은 자리에 코드 검증을 얹는 구조다.

> **자체 App ID를 발급받으면 노출이 오히려 커진다.** 480일 때는 우리 방이 남의 게임 로비 사이에 묻히지만,
> 자체 App ID에서는 목록이 전부 우리 게임 방이 된다. 그때 2번 방어가 없으면 실질적으로 무방비다.

## 4. 난입(Mid-match Join) — 사실 확인부터

**"난입을 허용할까"가 아니라 "이미 허용되어 있는 것을 유지할까"가 정확한 질문이다.**

현재 [`LobbyController.TryConnectToStartedGame()`](../../../Assets/Scripts/UI/LobbyController.cs)은
게스트가 로비에 들어왔을 때 `gh_game_started`가 `"1"`이면 **즉시 `ConnectToSteamHost`를 호출한다.**
호스트가 게임을 시작한 뒤 초대를 수락한 친구는 지금도 진행 중인 세션에 들어간다.

### 기술적으로 준비된 것

| 항목 | 상태 |
| --- | --- |
| NGO 씬 동기화 (늦게 접속한 클라가 `Game` 씬 로드) | ✅ Scene Management 활성 |
| 문 상태 | ✅ `NetworkVariable<bool>` — 현재 값으로 스냅 |
| 가구 위치 | ✅ 씬 배치 `NetworkObject` + `NetworkTransform` |
| 홀더 슬롯 | ✅ `NetworkList` 복제 |
| 방 프리셋 배치 결과 | ✅ 스폰이 아니라 이동이므로 트랜스폼으로 따라옴 |
| 빌드 호환성 검사 | ✅ 로비 단계 `gh_net_fingerprint` |

### 준비되지 않은 것

| 항목 | 문제 |
| --- | --- |
| ~~**스폰 위치**~~ | ~~난입자가 벽 안이나 다른 플레이어 위에 스폰될 수 있다~~ → **2026-08-21 해결.** `PlayerSpawnRegistry`가 선호 지점부터 빈자리를 찾고, 전부 막히면 주변으로 밀어낸다 |
| **정원 검사** | 로비 정원(4)과 세션 정원이 별개다. 로비를 나갔다 들어온 인원이 있으면 어긋날 수 있다 |
| **게임 규칙** | 승패·라운드가 아직 TBD. 난입 허용 여부는 **본래 게임 규칙에 종속된 결정**이다 |

### 권고

**당분간 유지한다. 단, 아래 조건부다.**

- 지금 막을 이유가 약하다. 승패 조건이 없어서 **난입으로 잃거나 얻을 것이 없고**, 친구 초대 경로가
  자연스럽게 동작하는 편이 UX가 낫다.
- 다만 **스폰 안전성은 먼저 고쳐야 한다.** 난입자가 벽에 끼는 건 규칙과 무관한 순수 결함이다.
  → 스폰 지점 선택 시 **점유 여부를 확인**하고, 전부 막혀 있으면 가장 가까운 빈 지점으로 밀어낸다.
- `gh_joinable` 키를 두어 정책을 **데이터로 표현**한다. 나중에 라운드가 생기면 값만 바꾸면 된다.
- **라운드·승패 조건이 확정되는 순간 이 절을 다시 연다.** 그때 "라운드 중 난입 금지, 라운드 사이 허용"
  같은 형태가 될 가능성이 높다.
